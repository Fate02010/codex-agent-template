# Skill: requirements-research — 需求调研与澄清输入整理

## 1. Purpose

本 Skill 的职责是把“想法级、碎片化、低结构化”的输入，整理为后续可执行的需求基础，而不是直接进入设计或开发。

核心职责：

1. 从业务想法、会议纪要、竞品资料、口头描述、已有文档中提炼有效需求信息。
2. 输出调研结论，包括业务目标、用户角色、典型场景、业务流程、关键规则、风险与待确认项。
3. 将需求输入整理为可直接给 `prd-compose` 与 OpenSpec proposal 使用的结构化材料。
4. 形成“已明确 vs 待澄清”边界，避免后续 PRD 编写阶段反复返工。

边界声明：

- 本 Skill 不输出代码。
- 本 Skill 不直接产出详细设计（架构/API/数据模型）。
- 本 Skill 不跳过需求澄清直接进入开发实现。

## 2. When to Use

以下场景应触发本 Skill：

1. 项目从 0 到 1，只有一个初步产品想法。
2. 业务资料零散，缺少可直接写 PRD 的结构化输入。
3. 需求边界模糊，需要先做澄清再决定 MVP。
4. 有新增功能需求，需要先评估业务影响范围与边界。
5. 正式 PRD 编写前，需要沉淀调研结论与问题清单。

## 3. Inputs

执行时按优先级读取输入：

必选输入：

1. 用户给出的产品想法（口述/文本均可）。
2. 业务背景资料（行业背景、商业目标、组织目标）。
3. 会议纪要或聊天记录摘要。
4. 竞品信息或行业参考资料。

可选输入（存在则必须使用）：

1. Word PRD 初稿。
2. Sketch / Figma / 原型截图。
3. OpenSpec `project.md`。
4. OpenSpec `changes/*` 下的 `proposal.md`、`design.md`、`specs/`、`tasks.md`。

输入处理规则：

- 先记录“信息来源”，再做结论。
- 对来源不明或二手转述信息，必须标识可信度。
- 输入不足时可先输出可评审草案，但必须列出【待确认】问题。

## 4. Outputs

本 Skill 的输出必须落盘，禁止只在对话中口头说明。

固定输出文件：

1. `docs/00-research/RESEARCH_SUMMARY.md`
2. `docs/01-requirements/REQUIREMENTS_CLARIFIED.md`
3. `docs/01-requirements/RESEARCH_QUESTIONS.md`

可选输出：

1. `docs/01-requirements/PRD_CHAPTER_SUGGESTION.md`（用于给后续 PRD 的章节建议）

为适配当前模板主链（`prd-compose` 仍读取 `docs/00-research/REQUIREMENTS_CLARIFIED.md`），执行时增加兼容动作：

1. 若主输出写入 `docs/01-requirements/REQUIREMENTS_CLARIFIED.md`，需同步一份同内容到 `docs/00-research/REQUIREMENTS_CLARIFIED.md`。
2. 两份文件内容必须保持一致，文档信息区记录“主文件/兼容镜像”关系。

上述输出内容至少覆盖：

1. 项目背景
2. 业务目标
3. 目标用户/角色
4. 关键场景
5. 业务流程
6. 关键规则
7. 风险点
8. 待确认项
9. 需求边界（MVP / 非 MVP）

## 5. Rules

执行时必须遵守以下规则：

1. 必须优先提取事实，不得直接脑补业务结论。
2. 信息不足时可做合理归纳，但必须标记【推断】。
3. 不确定内容必须标记【待确认】。
4. 同一需求来源出现冲突时，必须单列“冲突项”并标明来源与影响。
5. 输出必须严格区分“已明确”和“待澄清”。
6. 输出必须可直接作为后续 PRD 与 OpenSpec proposal 输入。
7. 不输出代码，不创建业务实现文件。
8. 不直接输出详细设计文档（不替代 `solution-design`）。
9. 不直接跳到开发实现（不替代 `dev-implement`）。
10. 使用项目统一标记规范：【新增】【修改】【删除】【待确认】【风险】【设计推断】【冲突】。
11. 文档信息区必须包含：文档类型、生成 Skill、上游输入、版本、日期、状态。

## 6. Research Dimensions

本 Skill 必须从以下维度完成调研，且每个维度都要有结论或待确认项：

1. 项目目标：项目成功判定、阶段目标、业务优先级。
2. 业务价值：为谁创造什么价值，价值如何体现。
3. 用户角色：角色类型、职责、使用频率、权限差异。
4. 使用场景：高频场景、关键任务场景、异常场景。
5. 核心流程：主流程、分支流程、中断与回退路径。
6. 数据对象：核心实体、关键字段、对象关系。
7. 业务规则：约束条件、校验规则、状态流转规则。
8. 异常场景：失败路径、错误反馈、补救机制。
9. 权限边界：角色可见性、可操作性、审批边界。
10. MVP 与非 MVP 范围：首版必须做与可延后能力划分。
11. 已知风险与依赖：外部系统依赖、组织依赖、时间风险、合规风险。

## 7. Steps

按以下步骤执行，不可跳步：

### 步骤 1：读取并整理输入材料

1. 汇总用户提供的全部资料与上下文。
2. 建立“来源清单”，记录每条信息出处。
3. 初步分组为：目标、角色、场景、规则、边界、风险。

### 步骤 2：识别业务目标与核心对象

1. 提炼项目目标和业务价值。
2. 识别核心业务对象与对象关系。
3. 标记无法直接确认的对象定义为【待确认】。

### 步骤 3：提取用户角色与场景

1. 明确角色分类与权限差异。
2. 提取典型使用场景和关键任务链路。
3. 对冲突场景来源做并列记录。

### 步骤 4：梳理主流程与关键规则

1. 输出业务主流程与关键分支。
2. 归纳输入校验、状态流转、业务约束规则。
3. 明确异常场景与风险触发点。

### 步骤 5：归纳冲突、缺失、待确认项

1. 单列冲突项并标注来源。
2. 单列缺失信息，指出对后续 PRD 的影响。
3. 形成结构化问题清单（问题、原因、影响、建议确认人）。

### 步骤 6：输出调研总结

1. 写入 `docs/00-research/RESEARCH_SUMMARY.md`。
2. 覆盖背景、目标、角色、场景、流程、规则、边界、风险、冲突。
3. 明确“已明确事项”与“待澄清事项”。

### 步骤 7：输出澄清后的需求说明

1. 写入 `docs/01-requirements/REQUIREMENTS_CLARIFIED.md`。
2. 对可确认需求形成结构化结论。
3. 同步兼容镜像到 `docs/00-research/REQUIREMENTS_CLARIFIED.md`。

### 步骤 8：输出问题清单

1. 写入 `docs/01-requirements/RESEARCH_QUESTIONS.md`。
2. 每条问题至少包含：编号、问题描述、来源、影响、建议答案方向、状态。
3. 按优先级排序（P0/P1/P2），供后续会议确认。

### 步骤 9：可选输出 PRD 章节建议

1. 若信息已足够，输出 `PRD_CHAPTER_SUGGESTION.md`。
2. 给出 PRD 建议章节与每章应承载的关键信息。

## 8. Quality Gate

完成前必须全部满足：

- [ ] 已提炼明确的业务目标。
- [ ] 已识别用户角色与关键场景。
- [ ] 已归纳核心流程与关键规则。
- [ ] 已列出冲突项、待确认项与风险项。
- [ ] 输出已能支撑后续 PRD 编写与 OpenSpec proposal。
- [ ] “已明确 / 待澄清”边界清晰，便于产品、架构、开发共用。
- [ ] 输出文档结构清晰、术语统一、可追溯来源明确。

任一项不满足时，不得标记完成，需回退补齐。

## 9. Example

示例输入（极简）：

`我想做一个会员管理系统。`

本 Skill 应输出的核心内容示例：

1. 目标用户
   - 运营人员：维护会员信息、处理会员状态。
   - 客服人员：查询会员资料与历史记录。
   - 管理员：配置会员等级规则与权限策略。

2. 核心模块
   - 会员档案管理
   - 会员等级管理
   - 积分与成长值管理
   - 会员标签与分群
   - 会员查询与统计看板

3. MVP 能力
   - 会员列表/详情/编辑
   - 会员等级规则配置（基础版）
   - 积分流水查询
   - 基础权限控制（管理员/运营/客服）

4. 待确认问题
   - 会员唯一标识以手机号、邮箱还是外部 ID 为准？
   - 等级升级规则由手工触发还是自动计算？
   - 积分是否存在过期机制，过期规则如何定义？
   - 是否需要对接外部 CRM/订单系统？
   - 首期是否需要导入历史会员数据？

5. 调研结论（摘要）
   - 项目价值：提升会员运营效率和精细化分层能力。
   - 目标边界：优先建设后台管理能力，首期不做复杂营销自动化。
   - 风险依赖：会员主数据口径与外部系统对接规则未定，属于上线前阻塞项。

---

执行提示（给 Codex）：

1. 先做“调研与澄清”，再让下游做 PRD，不要跨阶段。
2. 有把握的写“已明确”，没把握的标“【待确认】”，不要混写。
3. 所有结论尽可能绑定来源，避免不可追溯的主观判断。
