# Skill: requirement-clarify — 需求澄清

## 触发条件

当 `RESEARCH_SUMMARY.md` 已生成，其中包含矛盾、缺口或模糊信息需要与利益相关者确认时使用。

## 输入

- `docs/00-research/RESEARCH_SUMMARY.md` — 需求调研摘要

## 输出

- `docs/00-research/REQUIREMENTS_CLARIFIED.md` — 需求澄清记录

## 执行流程

### 步骤 1：读取调研摘要

1. 读取 `RESEARCH_SUMMARY.md`
2. 重点关注第 8 章（矛盾与缺口）和第 9 章（待澄清事项）
3. 同时扫描全文，识别隐含的模糊点（如"大概"、"可能"、"等"、"若干"等模糊用语）

### 步骤 2：生成澄清问题清单

对每个矛盾、缺口或模糊点，生成结构化的澄清问题：

```markdown
### CQ-NNN: [问题标题]
- **来源**：RESEARCH_SUMMARY.md § [章节/编号]
- **问题描述**：具体说明发现的问题
- **选项/建议**：列出可能的解决方案及各自利弊
- **推荐默认值**：如果无法获得明确答复，建议采用的默认值
```

按优先级分类：

| 优先级 | 含义 | 处理要求 |
|---|---|---|
| 必须澄清 | 阻塞 PRD 编写，无法给出合理默认值 | 必须获得明确答复 |
| 建议澄清 | 影响需求质量，但有合理默认值 | 建议确认，可用默认值 |
| 可选澄清 | 优化项，不影响核心功能 | 可推迟到后续迭代 |

### 步骤 3：与用户交互

1. 将完整的澄清问题清单呈现给用户，按优先级排序
2. **"必须澄清"问题**：逐一与用户确认，等待明确答复
3. **"建议澄清"问题**：呈现推荐默认值，询问用户是否接受
4. **"可选澄清"问题**：告知用户可延后处理

> 本 Skill 是工作链中**唯一需要多轮用户交互**的环节。

### 步骤 4：记录决策

对每个 CQ 问题：

1. 记录用户的决策结果
2. 记录决策依据（用户给出的理由或上下文）
3. 将 `【待确认】` 替换为 `【澄清结论】`
4. 如果用户无法回答某些问题，标记为 `【风险】` 并注明采用的默认值

### 步骤 5：输出 REQUIREMENTS_CLARIFIED.md

将澄清结果写入 `docs/00-research/REQUIREMENTS_CLARIFIED.md`：

1. **澄清问题清单**：所有 CQ 问题及其决策结果
2. **澄清后功能要点**：基于 `RESEARCH_SUMMARY.md` 第 5 章更新后的功能要点表，附带关联的 CQ 编号和确认状态
3. **确认的业务规则**：经用户确认的业务规则
4. **确认的约束与边界**：经用户确认的系统约束
5. **遗留风险**：标记为 `【风险】` 的未解决项及其默认值

### 步骤 6：提示下一步

澄清完成后提示用户：
- 下一步使用 `prd-compose` 将澄清后的需求编写为正式 PRD

## 注意事项

- 本 Skill 涉及用户交互，**不得替用户做决策**
- 如果 `RESEARCH_SUMMARY.md` 的矛盾与缺口章节为空，仍需扫描全文寻找隐含模糊点，但 Skill 可能快速完成
- 澄清问题必须具体、可操作，不能写"请描述需求"这样的泛泛提问
- 每个问题必须回溯到 `RESEARCH_SUMMARY.md` 的具体章节/条目
- CQ 编号必须唯一且连续
- 澄清记录是后续 `prd-compose` 的核心输入，必须完整记录所有决策
