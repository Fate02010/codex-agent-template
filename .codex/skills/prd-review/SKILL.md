# Skill: prd-review — PRD 评审

## 触发条件

当需要评审 PRD（产品需求文档）时使用本 Skill。

## 输入

- `docs/01-requirements/PRD_RAW.md` — 原始 PRD 文档

## 输出

- `docs/01-requirements/PRD_REVIEW_ISSUES.md` — PRD 评审问题清单

## 执行流程

### 步骤 1：读取 PRD

读取 `docs/01-requirements/PRD_RAW.md`，理解业务背景和需求范围。

### 步骤 2：逐项评审

按以下维度逐项检查 PRD，记录发现的问题：

| 评审维度 | 检查要点 |
|---|---|
| 完整性 | 是否覆盖了所有核心功能？是否有遗漏的流程分支？ |
| 一致性 | 前后描述是否矛盾？术语是否统一？ |
| 明确性 | 是否有模糊表述（"等"、"可能"、"大概"）？规则是否可量化？ |
| 可实现性 | 技术上是否可行？是否有未说明的技术依赖？ |
| 可测试性 | 每条需求是否可以写出明确的测试用例？验收标准是否清晰？ |
| 异常场景 | 异常流是否描述充分？错误提示是否明确？ |
| 边界条件 | 数值范围、字符长度、时间限制等边界是否定义？ |
| 权限控制 | 不同角色的操作权限是否明确？ |
| 数据流 | 数据从哪来、到哪去、怎么变化是否清晰？ |
| 非功能需求 | 性能、安全、兼容性要求是否提及？ |

### 步骤 3：问题分类与定级

对每个问题进行分类和定级：

| 级别 | 含义 | 处理要求 |
|---|---|---|
| 🔴 阻塞 | 无法继续设计或开发 | 必须在整改阶段解决 |
| 🟡 重要 | 影响设计质量或有歧义 | 建议在整改阶段解决 |
| 🟢 建议 | 优化建议，不影响核心功能 | 可在后续迭代处理 |

### 步骤 4：输出问题清单

将所有问题按以下格式写入 `docs/01-requirements/PRD_REVIEW_ISSUES.md`：

```markdown
# PRD 评审问题清单

## 文档信息
- 文档类型：产物
- 生成 Skill：`prd-review`
- 上游输入：`PRD_RAW.md`
- 版本：v1.0
- 日期：YYYY-MM-DD
- 状态：评审中 / 已冻结

## 评审信息
- 评审日期：YYYY-MM-DD
- PRD 来源：`docs/01-requirements/PRD_RAW.md`
- 评审结论：[通过 / 有条件通过 / 不通过]

## 问题统计
| 级别 | 数量 |
|---|---|
| 🔴 阻塞 | N |
| 🟡 重要 | N |
| 🟢 建议 | N |

## 问题清单

### 🔴 阻塞问题

#### ISSUE-001: [问题标题]
- **所在章节**：PRD 章节标题路径（如：`4. 功能需求 > F001`）
- **原文引用**：> 引用原文
- **问题描述**：具体说明问题
- **建议**：如何修改

### 🟡 重要问题
...

### 🟢 建议事项
...

## 变更记录
| 版本 | 日期 | 说明 |
|---|---|---|
| v1.0 | YYYY-MM-DD | 初始评审 |
```

### 步骤 5：给出评审结论

| 结论 | 条件 |
|---|---|
| 通过 | 无阻塞和重要问题 |
| 有条件通过 | 无阻塞问题，有重要问题但不影响核心架构 |
| 不通过 | 有阻塞问题，必须整改后重新评审 |

### 步骤 6：提示下一步

评审完成后提示用户：
- 下一步使用 `prd-rectify` 进行 PRD 整改

## 注意事项

- 评审基于事实，引用 PRD 原文指出问题
- 每个问题必须给出具体修改建议，不能只说"不清楚"
- 不要在评审阶段自行脑补需求，只标记问题
