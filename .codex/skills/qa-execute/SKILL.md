# Skill: qa-execute — 测试执行

## 触发条件

当测试计划和测试用例已就绪（`TEST_PLAN.md` 和 `TEST_CASES.md` 已生成），且代码已完成开发实现时，使用本 Skill 执行测试并生成测试报告。

## 前置条件

- `docs/03-testing/TEST_PLAN.md` 和 `TEST_CASES.md` 已生成（非模板状态）
- 后端代码可编译（`mvn compile` 通过）或前端代码可构建（`npm run build` 通过）
- 如果 `pom.xml` / `package.json` 不存在，结论只能是**阻塞**

## 完成标准

- `docs/03-testing/TEST_REPORT.md` 已生成，包含完整的执行统计和准出结论

## 输入

1. `docs/03-testing/TEST_PLAN.md` — 测试策略和范围
2. `docs/03-testing/TEST_CASES.md` — 待执行的测试用例
3. `backend/` 源代码（后端测试）
4. `frontend/` 源代码（前端测试）
5. `tests/AGENTS.md` — 测试规范（报告模板）

## 输出

1. `docs/03-testing/TEST_REPORT.md` — 测试执行报告
2. 更新后的 `docs/03-testing/TEST_CASES.md` — 填充实际结果和状态

## 执行流程

### 步骤 1：读取输入文档

1. 读取 `tests/AGENTS.md` 中“报告模板”相关章节，获取报告结构要求
2. 读取 `docs/03-testing/TEST_PLAN.md` 获取测试策略和执行顺序
3. 读取 `docs/03-testing/TEST_CASES.md` 获取全部待执行用例

### 步骤 2：执行后端单元测试

- 进入 `backend/` 项目根目录
- 执行命令：`mvn test`（或 `gradle test`）
- 范围：`src/test/` 下的 JUnit 5 测试
- 收集指标：通过数、失败数、错误数、跳过数
- 对每个失败用例：记录测试类、方法名、断言错误、堆栈摘要
- 如果 `pom.xml`/`build.gradle` 不存在，跳过并在报告中标注

### 步骤 3：执行后端集成测试

- 执行命令：`mvn verify -Dspring.profiles.active=test`（或等效命令）
- 范围：`@SpringBootTest`、MockMvc 测试
- 收集指标：同步骤 2
- 注意：如果测试数据库不可用，将集成测试标记为 BLOCKED

### 步骤 4：执行前端测试

- 进入 `frontend/web/`（或 `frontend/uniapp/`）
- 执行命令：`npx vitest run --reporter=json`
- 收集指标：通过数、失败数、跳过数、覆盖率（如可用）
- 如果 `package.json` 不存在，跳过并在报告中标注

### 步骤 5：校验测试代码与 TC 编号映射

在映射结果之前，先执行映射完整性校验：

1. 读取 `TEST_CASES.md` 中 `3. TC 与测试代码绑定规则` 下的 `3.1 测试代码映射表`（由 `qa-design` 生成）
   - 若缺失 `3.1 测试代码映射表`，将测试结论标记为 BLOCKED，并提示先回到 `qa-design` 补齐
2. 扫描测试代码中所有 `@DisplayName` / `it()` / `test()` 中的 TC 编号
3. 执行以下校验并记录结果：

| 校验项 | 通过条件 | 失败处理 |
|---|---|---|
| TC 覆盖率 | 每个 TC 编号在测试代码中都有对应方法 | 列出遗漏的 TC 编号，标记为 BLOCKED |
| 编号一致性 | 代码中的 TC 编号与 `TEST_CASES.md` 完全匹配 | 列出不匹配项，标记为异常 |
| 无孤立测试 | 测试代码中不存在无 TC 编号的业务测试方法 | 列出孤立测试，记入报告附录 |
| 方法名规范 | 后端方法名以 `tc_模块_序号` 开头 | 列出不规范项，记入报告附录 |

校验结果写入 `TEST_REPORT.md` 的新增"映射校验"章节。

### 步骤 6：映射测试结果到用例

对 `TEST_CASES.md` 中的每条测试用例：

1. 从测试执行结果中提取 `@DisplayName`（JUnit 5）或 `describe`/`it`（Vitest）描述中的 TC 编号
2. 通过 TC-XXX-NNN 编号匹配 `TEST_CASES.md` 中的对应用例
3. 填写"实际结果"字段
4. 设置"状态"为：通过 / 失败 / 阻塞 / 跳过
5. 对失败用例：记录观察到的实际行为
6. 验证 TC 编号模块部分与关联接口模块部分一致，不一致的标记为异常并记入报告
7. 无法通过 TC 编号自动匹配的测试结果，由 Agent 根据测试名称和用例标题进行语义匹配，并在报告中标注为"人工匹配"

### 步骤 7：计算统计指标

| 指标 | 计算方式 |
|---|---|
| 总用例数 | 统计所有 TC-XXX-NNN 条目 |
| 通过数 | 状态 = 通过 的数量 |
| 失败数 | 状态 = 失败 的数量 |
| 阻塞数 | 状态 = 阻塞 的数量 |
| 跳过数 | 状态 = 跳过 的数量 |
| 通过率 | 通过数 / (总数 - 阻塞数 - 跳过数) × 100% |
| 后端覆盖率 | 来自 JaCoCo（如可用），否则标注 — |
| 前端覆盖率 | 来自 Vitest coverage（如可用），否则标注 — |

### 步骤 8：输出 TEST_REPORT.md

按 `tests/AGENTS.md` 的报告模板约束，将结果写入 `docs/03-testing/TEST_REPORT.md`：

### 步骤 9：更新 TEST_CASES.md

将每条测试用例的实际结果和状态回写到 `TEST_CASES.md` 中。

### 步骤 10：提示下一步

- 如果全部通过：工作流完成，具备发布条件
- 如果存在失败：使用 `defect-fix` 修复缺陷，修复后重新执行 `qa-execute`

## 注意事项

- 如果构建工具尚未配置（无 `pom.xml`、无 `package.json`），在报告中标记为阻塞项，并建议先执行 `project-init`
- 测试执行是**真实执行** — Agent 运行实际的构建和测试命令
- 测试执行期间**不修改源代码**，只写入文档文件
- 如果测试环境依赖（MySQL、Redis）不可用，将受影响的测试标记为 BLOCKED，不标记为失败
- 按 `TEST_PLAN.md` 定义的执行顺序执行：冒烟（P0）→ 主流程（P1）→ 异常流（P1-P2）→ 边界值（P2-P3）
