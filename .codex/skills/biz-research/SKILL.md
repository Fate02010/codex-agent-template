# Skill: biz-research — 需求调研与信息归纳

## 触发条件

当用户提供原始业务资料（业务文档、调研材料、访谈记录、竞品分析、Word PRD、设计稿等），需要进行系统性调研、信息归纳和需求澄清时使用。

## 前置条件

- 至少有一份输入材料

## 输入

- 以下一种或多种：
  - Word 文档（.docx 文件）
  - PDF 文档（.pdf 文件）
  - 设计稿图片（.png、.jpg、Sketch 导出图、Figma 截图）
  - `.sketch` 源文件对应的导出图片、页面清单或结构化说明
  - 纯文本文件、会议纪要、访谈记录
  - 竞品分析报告
  - 用户研究数据
  - 商业策略/立项文档
- 可选：用户口头补充的项目背景信息

## 输出

1. `docs/00-research/RESEARCH_SUMMARY.md` — 结构化的需求调研摘要
2. `docs/00-research/REQUIREMENTS_CLARIFIED.md` — 需求澄清记录（如有待澄清项）

## 完成标准

- `RESEARCH_SUMMARY.md` 所有章节已填写，无空章节
- 如存在矛盾或缺口，`REQUIREMENTS_CLARIFIED.md` 中所有 CQ 问题已有决策结果
- `REQUIREMENTS_CLARIFIED.md` 始终生成（如无待澄清项，标注"无待澄清事项，全部功能要点直接确认"）

## 执行流程

本 Skill 分为两个阶段：**阶段一**为调研归纳，**阶段二**为需求澄清。阶段二在调研发现矛盾、缺口或模糊信息时触发。

---

### 阶段一：调研归纳

#### 步骤 1：清点并分类源材料

列举用户提供的所有文件，创建材料清单表：

| 序号 | 文件名 | 类型 | 内容分类 |
|---|---|---|---|
| 1 | xxx.docx | Word 文档 | 业务需求 / 调研报告 / 竞品分析 / … |

按类型分类处理方式：

| 类型 | 处理方式 |
|---|---|
| Word/PDF 文档 | 读取全文，保留标题层级和段落结构 |
| 设计稿图片 | 视觉分析，识别 UI 元素、页面流程和隐含需求 |
| 纯文本/会议纪要 | 提取关键信息点和决策项 |
| 竞品分析报告 | 提取功能对比和差异化要点 |

#### 步骤 2：从文本材料中提取主题信息

对每份文本材料，按以下主题提取和组织：

| 提取主题 | 提取规则 |
|---|---|
| 业务目标 | 识别项目背景、商业目标、KPI 指标 |
| 用户场景 | 识别用户角色、使用场景、用户旅程 |
| 功能要点 | 识别功能描述、特性列表、需求条目 |
| 业务规则 | 识别条件逻辑、校验规则、业务约束 |
| 技术约束 | 识别技术选型、性能要求、兼容性约束 |
| 非功能需求 | 识别安全、性能、可用性相关要求 |

**关键原则：保留原始语言和详细程度，不得杜撰需求。**

#### 步骤 3：分析视觉材料

对每张设计稿/高保真图执行以下分析：

1. **识别页面/屏幕名称**：根据标题栏、导航位置推断
2. **列举 UI 元素**：按钮、表单、表格、导航、弹窗、标签页等
3. **推断用户操作流程**：从布局推断用户交互路径
4. **记录数据字段**：表单中可见的字段名、类型、是否必填
5. **标注状态指示**：错误状态、空状态、加载状态、条件显示的 UI

所有从设计稿推断的内容标记为 `【设计推断】`。

#### 步骤 4：交叉比对与矛盾识别

对比所有材料来源：

1. **识别矛盾**：不同材料对同一功能的描述不一致，标记为 `【冲突】`
2. **识别缺口**：某些场景或功能只在部分材料中提及，信息不完整
3. **识别假设**：推断但未被任何材料明确说明的内容
4. 将所有矛盾和缺口记录到"矛盾与缺口"章节
5. 将需要确认的条目记录到"待澄清事项"章节

#### 步骤 5：输出 RESEARCH_SUMMARY.md

将整理后的内容写入 `docs/00-research/RESEARCH_SUMMARY.md`，并按文档中的章节标题组织（按标题匹配，不依赖章节序号）：

1. **输入材料清单**：所有源文件清单及来源信息
2. **调研结论摘要**：业务背景、项目目标、成功指标
3. **角色与场景**：角色清单和核心业务场景
4. **功能要点归纳**：功能条目、业务价值、来源、优先级
5. **业务规则与约束**：规则、限制与状态说明
6. **设计稿与页面观察**（如有）：页面观察与【设计推断】
7. **冲突、缺口与待澄清项**：冲突项、信息缺口、待澄清问题
8. **调研结论与建议下一步**：可直接推进项与风险说明

确保每个功能要点都标注了**来源材料**，便于后续追溯。

#### 步骤 6：判断是否需要澄清

- 如果 `RESEARCH_SUMMARY.md` 的 **"冲突、缺口与待澄清项"** 中无待澄清内容，**生成最小化的 REQUIREMENTS_CLARIFIED.md**：在 **"澄清结论汇总"** 中标注"无待澄清事项，全部功能要点直接确认"，并将 `RESEARCH_SUMMARY.md` 的 **"功能要点归纳"** 条目复制到 `REQUIREMENTS_CLARIFIED.md` 的 **"更新后的功能要点"**，状态全部标记为"已确认"。然后提示进入 `prd-compose`
- 如果存在待澄清项，**进入阶段二**

---

### 阶段二：需求澄清

> 本阶段是工作链中**唯一需要多轮用户交互**的环节。

#### 步骤 7：生成澄清问题清单

基于 `RESEARCH_SUMMARY.md` 的矛盾、缺口和模糊点，生成结构化的澄清问题：

```markdown
### CQ-NNN: [问题标题]
- **来源**：RESEARCH_SUMMARY.md（章节标题 + 条目编号）
- **问题描述**：具体说明发现的问题
- **选项/建议**：列出可能的解决方案及各自利弊
- **推荐默认值**：如果无法获得明确答复，建议采用的默认值
```

同时扫描全文识别隐含的模糊点（如"大概"、"可能"、"等"、"若干"等模糊用语）。

按优先级分类：

| 优先级 | 含义 | 处理要求 |
|---|---|---|
| 必须澄清 | 阻塞 PRD 编写，无法给出合理默认值 | 必须获得明确答复 |
| 建议澄清 | 影响需求质量，但有合理默认值 | 建议确认，可用默认值 |
| 可选澄清 | 优化项，不影响核心功能 | 可推迟到后续迭代 |

#### 步骤 8：与用户交互

1. 将完整的澄清问题清单呈现给用户，按优先级排序
2. **"必须澄清"问题**：逐一与用户确认，等待明确答复
3. **"建议澄清"问题**：呈现推荐默认值，询问用户是否接受
4. **"可选澄清"问题**：告知用户可延后处理

#### 步骤 9：记录决策

对每个 CQ 问题：

1. 记录用户的决策结果
2. 记录决策依据（用户给出的理由或上下文）
3. 将 `【待确认】` 替换为 `【澄清结论】`
4. 如果用户无法回答某些问题，标记为 `【风险】` 并注明采用的默认值

#### 步骤 10：输出 REQUIREMENTS_CLARIFIED.md

将澄清结果写入 `docs/00-research/REQUIREMENTS_CLARIFIED.md`：

1. **澄清问题清单**：所有 CQ 问题及其决策结果
2. **澄清结论汇总**：汇总 CQ 决策结果及对 PRD 的影响
3. **更新后的功能要点**：基于 `RESEARCH_SUMMARY.md` 中 `4. 功能要点归纳` 更新后的功能要点表，附带关联的 CQ 编号和确认状态
4. **更新后的业务规则与边界**：经用户确认的业务规则、约束和边界
5. **遗留风险**：标记为 `【风险】` 的未解决项及其默认值

---

### 步骤 11：提示下一步

- 下一步使用 `prd-compose` 将调研和澄清结果编写为正式 PRD

## 注意事项

- **不得杜撰需求**。如果信息不明确，列入"待澄清事项"
- 设计稿图片通过 Agent 的视觉能力分析，Agent 描述所见内容
- 对于大量材料，逐份处理以避免遗漏
- 保留 `【设计推断】` 和 `【冲突】` 标记，供后续流程消费
- `.sketch` 源文件默认不直接解析，需先转成可读图片或结构化说明
- 如果用户只提供了一份结构完整的 Markdown PRD 且无需调研，可跳过本 Skill 直接进入 `prd-review`
- 功能要点此阶段不使用正式 F 编号（F001），仅使用流水号，正式编号在 `prd-compose` 阶段分配
- 需求澄清阶段涉及用户交互，**不得替用户做决策**
- 澄清问题必须具体、可操作，每个问题必须回溯到 `RESEARCH_SUMMARY.md` 的具体章节
- CQ 编号必须唯一且连续
