# Skill: biz-research — 需求调研与信息归纳

## 触发条件

当用户提供原始业务资料（业务文档、调研材料、访谈记录、竞品分析、Word PRD、设计稿等），需要进行系统性调研和信息归纳时使用。

## 输入

- 以下一种或多种：
  - Word 文档（.docx 文件）
  - PDF 文档（.pdf 文件）
  - 设计稿图片（.png、.jpg、Sketch 导出图、Figma 截图）
  - 纯文本文件、会议纪要、访谈记录
  - 竞品分析报告
  - 用户研究数据
  - 商业策略/立项文档
- 可选：用户口头补充的项目背景信息

## 输出

- `docs/00-research/RESEARCH_SUMMARY.md` — 结构化的需求调研摘要

## 执行流程

### 步骤 1：清点并分类源材料

列举用户提供的所有文件，创建材料清单表：

| 序号 | 文件名 | 类型 | 内容分类 |
|---|---|---|---|
| 1 | xxx.docx | Word 文档 | 业务需求 / 调研报告 / 竞品分析 / … |

按类型分类处理方式：

| 类型 | 处理方式 |
|---|---|
| Word/PDF 文档 | 读取全文，保留标题层级和段落结构 |
| 设计稿图片 | 视觉分析，识别 UI 元素、页面流程和隐含需求 |
| 纯文本/会议纪要 | 提取关键信息点和决策项 |
| 竞品分析报告 | 提取功能对比和差异化要点 |

### 步骤 2：从文本材料中提取主题信息

对每份文本材料，按以下主题提取和组织：

| 提取主题 | 提取规则 |
|---|---|
| 业务目标 | 识别项目背景、商业目标、KPI 指标 |
| 用户场景 | 识别用户角色、使用场景、用户旅程 |
| 功能要点 | 识别功能描述、特性列表、需求条目 |
| 业务规则 | 识别条件逻辑、校验规则、业务约束 |
| 技术约束 | 识别技术选型、性能要求、兼容性约束 |
| 非功能需求 | 识别安全、性能、可用性相关要求 |

**关键原则：保留原始语言和详细程度，不得杜撰需求。**

### 步骤 3：分析视觉材料

对每张设计稿/高保真图执行以下分析：

1. **识别页面/屏幕名称**：根据标题栏、导航位置推断
2. **列举 UI 元素**：按钮、表单、表格、导航、弹窗、标签页等
3. **推断用户操作流程**：从布局推断用户交互路径
4. **记录数据字段**：表单中可见的字段名、类型、是否必填
5. **标注状态指示**：错误状态、空状态、加载状态、条件显示的 UI

所有从设计稿推断的内容标记为 `【设计推断】`。

### 步骤 4：交叉比对与矛盾识别

对比所有材料来源：

1. **识别矛盾**：不同材料对同一功能的描述不一致，标记为 `【冲突】`
2. **识别缺口**：某些场景或功能只在部分材料中提及，信息不完整
3. **识别假设**：推断但未被任何材料明确说明的内容
4. 将所有矛盾和缺口记录到"矛盾与缺口"章节
5. 将需要确认的条目记录到"待澄清事项"章节

### 步骤 5：综合输出 RESEARCH_SUMMARY.md

将整理后的内容写入 `docs/00-research/RESEARCH_SUMMARY.md`：

1. **调研背景与目标**：项目为什么做、核心商业目标
2. **输入材料清单**：所有源文件的清单表
3. **业务目标**：提炼的核心业务目标
4. **用户场景**：初步识别的用户角色和核心场景
5. **功能要点**：表格形式列出所有识别到的功能点，标注来源和优先级
6. **业务规则与约束**：跨材料汇总的业务规则
7. **竞品/调研发现**：如有竞品分析或市场调研，整理关键发现
8. **矛盾与缺口**：跨材料的矛盾和信息缺口表
9. **待澄清事项**：所有需要确认的条目

确保每个功能要点都标注了**来源材料**，便于后续追溯。

### 步骤 6：提示下一步

调研归纳完成后提示用户：
- 下一步使用 `requirement-clarify` 澄清矛盾和缺口

## 注意事项

- **不得杜撰需求**。如果信息不明确，列入"待澄清事项"
- 设计稿图片通过 Agent 的视觉能力分析，Agent 描述所见内容
- 对于大量材料，逐份处理以避免遗漏
- 保留 `【设计推断】` 和 `【冲突】` 标记，供后续流程消费
- 如果用户只提供了一份结构完整的 Markdown PRD 且无需调研，可跳过本 Skill 直接进入 `prd-review`
- 功能要点此阶段不使用正式 F 编号（F001），仅使用流水号，正式编号在 `prd-compose` 阶段分配
