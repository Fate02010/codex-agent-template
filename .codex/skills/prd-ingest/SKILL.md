# Skill: prd-ingest — 原始需求导入

## 触发条件

当用户提供的原始需求资料为非 Markdown 格式时使用本 Skill。支持的格式包括：Word 文档（.docx）、PDF 文档、设计稿截图/导出图（Sketch、Figma 等）。

## 输入

- 以下一种或多种：
  - Word 文档（.docx 文件）
  - PDF 文档（.pdf 文件）
  - 设计稿图片（.png、.jpg、Sketch 导出图、Figma 截图）
- 可选：用户口头补充的项目背景信息

## 输出

- `docs/01-requirements/PRD_RAW.md` — 从原始资料中提取的结构化初始 PRD

## 执行流程

### 步骤 1：识别并读取源文件

列举用户提供的所有文件，按类型分类：

| 类型 | 处理方式 |
|---|---|
| Word/PDF 文档 | 读取全文内容，保留标题层级和段落结构 |
| 设计稿图片 | 视觉分析每张图，识别 UI 元素、页面流程和隐含需求 |

### 步骤 2：从文档中提取结构化内容

从 Word/PDF 源文件中提取并组织以下信息：

| 提取内容 | 提取规则 |
|---|---|
| 项目背景 | 识别开头概述/背景章节 |
| 功能需求 | 识别编号或列表形式的功能描述 |
| 用户角色 | 识别角色/权限相关描述 |
| 业务规则 | 识别条件逻辑、校验规则、业务约束 |
| 非功能需求 | 识别性能、安全、兼容性相关描述 |
| 术语定义 | 识别专有名词和定义 |

保留原始语言和详细程度，**不得杜撰需求**。

### 步骤 3：从设计稿图片中提取结构化内容

对每张设计稿图片执行以下分析：

1. **识别页面/屏幕名称**：根据标题栏、导航位置推断
2. **列举 UI 元素**：按钮、表单、表格、导航、弹窗、标签页等
3. **推断用户操作流程**：从布局推断用户交互路径
4. **记录数据字段**：表单中可见的字段名、类型、是否必填
5. **标注状态指示**：错误状态、空状态、加载状态、条件显示的 UI
6. **按页面分组记录**到"设计稿清单"章节

### 步骤 4：合并与去重

- 将文档提取内容和设计稿提取内容合并
- 设计稿中出现但文档未提及的字段或功能，标记为 `【设计推断】`
- 文档中描述但设计稿中不可见的逻辑，保持原样
- 文档文字与设计稿存在矛盾的，标记为 `【冲突】`

### 步骤 5：输出 PRD_RAW.md

将整理后的内容写入 `docs/01-requirements/PRD_RAW.md`，使用以下结构：

```markdown
# 原始 PRD（导入）

## 文档信息
- 源文件：[列出所有输入文件名]
- 导入日期：YYYY-MM-DD
- 状态：待评审

## 1. 项目概述

## 2. 用户角色（如可识别）

## 3. 功能需求

### FR-001: [功能名称]
- **来源**：[文档名称 / 设计稿文件名]
- **描述**：...
- **UI 元素（来自设计稿）**：...
- **业务规则**：...
- **标记**：【设计推断】/【冲突】（如适用）

## 4. 非功能需求

## 5. 设计稿页面清单

| 页面 | 源文件 | 关键元素 | 关联 FR |
|---|---|---|---|

## 6. 待确认事项

> 汇总所有标记为【设计推断】或【冲突】的条目，需要产品/业务方确认。

## 变更记录
| 版本 | 日期 | 说明 |
|---|---|---|
```

### 步骤 6：提示下一步

导入完成后提示用户：
- 下一步使用 `prd-review` 对 `PRD_RAW.md` 进行评审

## 注意事项

- **不得杜撰需求**。如果信息不明确，列入"待确认事项"章节
- 设计稿图片通过 Agent 的视觉能力分析，Agent 描述所见内容，不运行 OCR 脚本
- 输出的 `PRD_RAW.md` 结构较松散，经过 `prd-review` 和 `prd-rectify` 后会获得完整结构
- 对于大型文档，逐章节处理以避免遗漏内容
- 如果用户同时提供了 Markdown 格式的 PRD，则无需使用本 Skill，直接进入 `prd-review`
