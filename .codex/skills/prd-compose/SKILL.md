# Skill: prd-compose — 详细需求文档编写

## 触发条件

当需求已完成澄清（`REQUIREMENTS_CLARIFIED.md` 已生成），需要将澄清后的需求结构化为正式 PRD 时使用。

## 输入

1. `docs/00-research/REQUIREMENTS_CLARIFIED.md` — 需求澄清记录
2. `docs/00-research/RESEARCH_SUMMARY.md` — 调研摘要（补充来源追溯）
3. 可选：设计稿图片（Sketch/Figma 导出图）— 用于补充 UI 相关需求细节

## 输出

- `docs/01-requirements/PRD_RAW.md` — 结构化的初始 PRD

## 执行流程

### 步骤 1：读取澄清结果与调研摘要

1. 读取 `REQUIREMENTS_CLARIFIED.md` 获取已确认的功能要点、业务规则、约束和遗留风险
2. 读取 `RESEARCH_SUMMARY.md` 获取原始来源信息，用于追溯标注

### 步骤 2：分配正式需求编号

将 `REQUIREMENTS_CLARIFIED.md` 第 2 章的功能要点转化为正式编号：

1. 按功能模块分组
2. 分配 F 编号：F001、F002、…
3. 建立编号映射表：功能要点编号 → F 编号 → 关联 CQ 编号

| 模块 | F 编号 | 功能要点 | 关联 CQ |
|---|---|---|---|

### 步骤 3：结构化每个需求

对每个 F 编号，按以下结构详细展开：

```markdown
### F001: [功能名称]

- **描述**：功能的详细描述
- **角色**：使用该功能的用户角色
- **前置条件**：执行前必须满足的条件
- **主流程**：
  1. 步骤 1
  2. 步骤 2
  3. …
- **字段清单**：

| 字段名 | 类型 | 必填 | 校验规则 | 说明 |
|---|---|---|---|---|

- **业务规则**：该功能涉及的业务规则
- **异常场景**：异常情况及处理方式
- **边界条件**：数值范围、字符长度、时间限制等
```

信息来源优先级：
1. `REQUIREMENTS_CLARIFIED.md` 中已确认的内容（最高优先）
2. `RESEARCH_SUMMARY.md` 中无争议的内容
3. 设计稿中推断的内容（标记 `【设计推断】`）

### 步骤 4：分析设计稿补充 UI 细节

如果用户提供了设计稿图片：

1. 对每张设计稿进行视觉分析
2. 识别页面名称、UI 元素、交互流程、数据字段
3. 将发现的 UI 细节补充到对应 F 编号的字段清单和主流程中
4. 从设计稿推断但未在文字需求中明确的内容，标记为 `【设计推断】`
5. 设计稿与澄清后文字有矛盾的，标记为 `【冲突】`
6. 整理设计稿页面清单表

### 步骤 5：编写非功能需求

从 `REQUIREMENTS_CLARIFIED.md` 中提取并结构化：

- **性能要求**：响应时间、并发量、数据量
- **安全要求**：认证、授权、数据保护
- **兼容性要求**：浏览器、设备、操作系统

### 步骤 6：编写全局异常与边界

汇总跨功能的通用异常场景和全局边界条件：

- 通用异常场景（网络异常、未登录、权限不足等）
- 全局边界条件（系统级约束）

### 步骤 7：输出 PRD_RAW.md

将完整需求写入 `docs/01-requirements/PRD_RAW.md`，使用以下结构：

```markdown
# 原始 PRD

## 文档信息
- 源文件：REQUIREMENTS_CLARIFIED.md + RESEARCH_SUMMARY.md
- 编写日期：YYYY-MM-DD
- 状态：待评审

## 1. 项目概述
### 1.1 项目背景
### 1.2 项目目标
### 1.3 项目范围

## 2. 用户角色
| 角色 | 描述 | 核心权限 |
|---|---|---|

## 3. 功能需求
### F001: [功能名称]
（完整结构，见步骤 3）

## 4. 异常与边界（全局）
### 4.1 通用异常场景
### 4.2 全局边界条件

## 5. 非功能需求
### 5.1 性能要求
### 5.2 安全要求
### 5.3 兼容性要求

## 6. 设计稿页面清单（如有设计稿）
| 页面 | 源文件 | 关键元素 | 关联 F 编号 |
|---|---|---|---|

## 7. 待确认事项
> 遗留风险和标记为【设计推断】/【冲突】的条目

## 8. 术语表
| 术语 | 定义 |
|---|---|

## 变更记录
| 版本 | 日期 | 说明 |
|---|---|---|
```

### 步骤 8：提示下一步

PRD 编写完成后提示用户：
- 下一步使用 `prd-review` 对 PRD 进行评审

## 注意事项

- **不得杜撰需求**。所有内容必须来自澄清记录或调研摘要，剩余不确定项放入"待确认事项"
- F 编号必须唯一且在模块内连续
- 追溯链：源材料 → RESEARCH_SUMMARY.md → REQUIREMENTS_CLARIFIED.md (CQ-xxx) → PRD_RAW.md (F-xxx)
- 保留 `【设计推断】` 和 `【冲突】` 标记，供下游 `prd-review` 消费
- 输出的 PRD_RAW.md 结构已接近 PRD_RECTIFIED.md，但仍需经过 `prd-review` 和 `prd-rectify` 正式冻结
- 设计稿分析使用 Agent 的视觉能力，非外部脚本
