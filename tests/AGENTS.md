# tests/AGENTS.md — 测试规范

## 1. 总则

测试是独立阶段，不是开发附属动作。所有测试产物存放于 `docs/03-testing/` 和 `tests/` 目录。

## 2. 测试类型与分层

| 测试类型 | 范围 | 存放位置 |
|---|---|---|
| 单元测试 | Domain Service、工具类 | `backend/src/test/` 或 `frontend/*/tests/unit/` |
| 集成测试 | Application Service、Repository、Controller | `backend/src/test/` |
| 接口测试 | REST API 端到端 | `tests/api/` |
| 前端测试 | 组件测试、E2E 测试 | `frontend/*/tests/` |
| 测试文档 | 测试计划、测试用例 | `docs/03-testing/` |

## 3. 用例模板

每条测试用例必须包含：

| 字段 | 说明 | 示例 |
|---|---|---|
| 用例编号 | 模块编号 + 序号 | TC-USER-001 |
| 用例标题 | 简要描述测试场景 | 正常创建用户 |
| 关联需求 | 对应 PRD 功能编号 | F001 |
| 关联接口 | 对应接口编号 | API-USER-001 |
| 优先级 | P0（冒烟）/ P1（核心）/ P2（一般）/ P3（边界） | P0 |
| 前置条件 | 执行前需要的环境和数据 | 用户已登录，数据库有测试数据 |
| 测试步骤 | 编号的操作步骤 | 1. 调用创建用户接口 2. 传入合法参数 |
| 预期结果 | 明确的验证点 | 返回 code=0，用户记录已入库 |
| 实际结果 | 执行后填写 | — |
| 状态 | 通过 / 失败 / 阻塞 / 跳过 | — |

## 4. 覆盖要求

每个功能模块至少覆盖以下场景：

| 场景类型 | 说明 | 优先级 |
|---|---|---|
| 主流程 | 正常业务路径 | P0 |
| 异常流 | 参数错误、权限不足、数据不存在 | P1 |
| 边界值 | 最大值、最小值、空值、特殊字符 | P2 |
| 权限 | 不同角色的访问控制 | P1 |
| 幂等性 | 重复提交不产生副作用 | P1 |
| 并发 | 并发操作数据一致性 | P2 |

## 5. 执行原则

按以下顺序执行测试：

1. **冒烟测试**（P0）— 验证核心功能可用
2. **主流程测试**（P1）— 验证所有正常业务路径
3. **异常流测试**（P1-P2）— 验证异常处理是否正确
4. **边界值测试**（P2-P3）— 验证边界条件处理

## 6. 报告模板

测试报告必须包含：

| 章节 | 内容 |
|---|---|
| 测试概要 | 测试范围、测试时间、测试环境 |
| 执行统计 | 总用例数、通过数、失败数、阻塞数、跳过数 |
| 通过率 | 通过数 / 总用例数 × 100% |
| 失败用例 | 失败用例清单及原因分析 |
| 阻塞项 | 阻塞测试的环境或依赖问题 |
| 风险项 | 影响发布的质量风险 |
| 结论 | 是否具备发布条件 |

## 7. 回归要求

- 每次修复缺陷后，必须补充对应的回归测试用例
- 回归用例标记：`[回归] TC-USER-001-R1`
- 发布前必须通过全部 P0 和 P1 回归用例

## 8. 缺陷记录规则

| 字段 | 说明 |
|---|---|
| 缺陷编号 | BUG-模块-序号 |
| 关联用例 | 发现缺陷的用例编号 |
| 严重程度 | 致命 / 严重 / 一般 / 轻微 |
| 复现步骤 | 与用例步骤一致或补充 |
| 预期结果 | 应该的行为 |
| 实际结果 | 实际的行为 |
| 状态 | 新建 / 修复中 / 已修复 / 已验证 / 已关闭 |

## 9. 禁止事项

- 禁止无用例直接测试（测试必须有用例支撑）
- 禁止跳过 P0 用例发布
- 禁止修复缺陷后不补回归用例
- 禁止测试用例不关联需求编号
