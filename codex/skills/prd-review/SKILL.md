# Skill: prd-review — PRD 评审

## 触发条件

当 `PRD_RAW.md` 已完成且需要进入整改冻结前评审时使用本 Skill。

以下场景不触发本 Skill：

- 仍在编写 PRD 初稿（应先使用 `prd-compose`）
- 已进入整改与冻结阶段（应使用 `prd-rectify`）
- 需要架构、接口、数据模型设计（应使用 `solution-design`）

## 输入

- `docs/01-requirements/PRD_RAW.md` — 原始 PRD 文档

## 输出

- `docs/01-requirements/PRD_REVIEW_ISSUES.md` — PRD 评审问题清单
- `docs/01-requirements/PRD_REVIEW_FAILFAST_REPORT.md` — Fail-fast 自动扫描报告

## 执行层级导读（Progressive Disclosure）

- `P0 必检（阻塞）`：Fail-fast 门禁、阻塞项识别、结论级别判定。
- `P1 扩展（覆盖）`：完整性/一致性/可实现性/可测试性等评审维度覆盖。
- `P2 参考（说明）`：示例与说明文本仅作参考，不参与放行。
- 执行顺序必须为：先过 `P0 Gate`，再进入 `P1`；`P2` 不得覆盖 `P0` 结论。

## 执行规则

1. `P0 Gate` 未通过时，评审结论必须为 `不通过`。
2. 规则去重：Fail-fast 主定义保留在评审维度与判定规则中，后续章节仅引用编号与结论。
3. 在进入人工逐项评审前，必须执行自动化 Fail-fast 扫描：
   - `scripts/run_prd_gate.sh --mode review --repo-root "$PWD"`
   - 任一门禁失败时必须直接输出 `不通过`，不得降级为建议项。

## 执行流程

### 步骤 0：P0 Gate（阻塞）

1. 校验 `PRD_RAW.md` 可读且结构可判定。
2. 若不可读或结构无法判定，输出 `BLOCKED/FAIL` 并停止，不进入步骤 1。

### 步骤 1：读取 PRD

读取 `docs/01-requirements/PRD_RAW.md`，理解业务背景和需求范围。

### 步骤 1.5：执行 Fail-fast 门禁扫描（P0 阻塞）

在进入逐项评审前，必须先执行 UI 可冻结门禁的自动化扫描：

#### 1. 信息层级检查
- 扫描每个 `FNNN` 的 `UI约束必填块`
- 验证：页面目标、主任务、首屏主任务区块是否明确
- 输出：信息层级缺失的功能清单

#### 2. 主按钮唯一性检查
- 扫描 `主操作` 字段，验证是否仅有 1 个主按钮
- 扫描 `次操作`、`危险操作`，验证是否与主操作冲突
- 输出：主按钮冲突的功能清单

#### 3. 文案中文化检查
- 扫描 `字段展示映射` 表格
- 检测是否存在技术字段直出（正则匹配：`_id$|_status$|^biz_|^user_`）
- 输出：技术字段直出的清单

#### 4. 状态标签完整性检查
- 扫描 `状态标签规则` 表格
- 验证每个状态是否包含：标签文案、颜色语义、禁用态规则、可点击态规则
- 输出：状态标签缺失的清单

#### 5. 交互闭环检查
- 扫描 `反馈规则` 表格
- 验证是否包含：空态、加载态、失败态、成功态
- 输出：反馈规则缺失的清单

#### 6. 页面类型与布局模板匹配检查
- 扫描 `页面类型` 和 `布局模板`
- 验证是否匹配（查看型→列表主视图，维护型→表单主视图，处理型→双栏处理视图）
- 输出：不匹配的功能清单

#### 7. 主任务首屏可见检查
- 扫描 `首屏主任务区块`
- 验证是否明确说明首屏可见信息
- 输出：首屏主任务区块缺失的功能清单

#### 8. 列表页前置重表单检查
- 扫描页面类型为“查看型页面”且布局模板为“列表主视图”的功能
- 验证是否存在“上重表单下长列表”布局，且无解耦策略
- 输出：存在前置重表单问题的功能清单

#### 9. 主任务跨屏依赖检查
- 扫描 `主任务滚动预算`
- 验证是否定义滚动预算，且超过 1 屏时是否有例外说明
- 输出：滚动预算缺失或超标的功能清单

#### 10. 双主流程冲突检查
- 扫描 `主操作`
- 验证是否存在多个主按钮或主动作链
- 输出：双主流程冲突的功能清单

#### 11. 工具栏顺序与分页语义检查
- 扫描 `工具栏顺序`
- 验证是否定义筛选->结果->分页顺序
- 输出：工具栏顺序缺失的功能清单

#### 12. 筛选后分页重置检查
- 扫描 `筛选后分页重置规则`
- 验证是否定义筛选后页码重置行为
- 输出：分页重置规则缺失的功能清单

#### 13. 门禁判定
- 若任一门禁项失败，直接标记 `🔴 阻塞` 并输出 `不通过` 结论
- 不再进入步骤 2 的逐项评审，直接生成问题清单

**输出到 PRD_REVIEW_ISSUES.md 的格式**：
```markdown
## Fail-fast 门禁检查结果

### ❌ 门禁未通过 / ✅ 门禁通过

| 门禁项 | 失败原因 | 影响功能 |
|---|---|---|
| 主按钮唯一性 | F001 存在 2 个主按钮 | F001 |
| 文案中文化 | F002 字段展示映射中存在 `user_id` 直出 | F002 |
| 状态标签完整性 | F003 状态标签缺失颜色语义 | F003 |
```

### 步骤 2：逐项评审

先消费步骤 1.5 的 Fail-fast 失败项，再补充人工审查问题，避免“Fail-fast 与评审维度”分裂。

按以下维度逐项检查 PRD，记录发现的问题：

| 评审维度 | 检查要点 |
|---|---|
| 完整性 | 是否覆盖了所有核心功能？是否有遗漏的流程分支、角色动作或页面映射？ |
| 一致性 | 前后描述是否矛盾？术语、字段、角色、页面、流程名称是否统一？ |
| 明确性 | 是否有模糊表述（“等”“可能”“大概”）？规则是否可量化？ |
| 可实现性 | 技术上是否可行？是否存在未说明的关键依赖、集成约束或数据流断点？ |
| 可测试性 | 每条需求是否可以写出明确测试用例？验收标准是否可直接转测试步骤或断言？ |
| 字段参数约束 | 字段是否补齐参数级约束：长度/精度、最小值/最大值、格式/枚举、空值策略、错误提示？ |
| 跨字段规则 | 是否明确跨字段依赖、互斥、联动、优先级与冲突处理规则？ |
| 状态流转 | 有生命周期的功能是否定义完整状态流转？无状态机的功能是否明确声明“无独立状态流转”？ |
| 权限控制 | 不同角色的操作权限、数据范围和关键动作是否明确？角色-权限-动作矩阵是否覆盖核心操作？ |
| 数据与契约影响 | 字段、业务规则、异常处理是否足以支撑接口设计和表结构设计？是否标记了“影响接口”与“影响表结构”？ |
| 关键流程可视化 | 关键业务流程是否提供伪流程图文本（步骤化流程）或等价结构化流程说明，且能落到字段与状态变化？ |
| 验收标准结构化 | 验收标准是否具备 Given/When/Then（或等价三段式）并可映射测试断言？ |
| 追溯性 | 来源材料、澄清结论、计划接口、计划数据表、计划测试是否具备下游可消费的追溯入口？ |
| 非功能需求 | 性能、安全、兼容性、日志与审计要求是否提及且量化（阈值/口径/验证方式）？ |

**注意：**
- 步骤 1.5 的 Fail-fast 门禁扫描已覆盖 UI 可冻结门禁检查清单
- 步骤 2 的逐项评审主要关注完整性、一致性、明确性、可实现性、可测试性等维度
- 若步骤 1.5 已标记 `🔴 阻塞`，则不进入步骤 2

`UI可冻结门禁检查清单（Fail-fast）`：

| 门禁项 | 检查要点 | 失败判定 |
|---|---|---|
| 信息层级清晰 | 页面目标、主任务、核心信息分区与阅读顺序是否明确，是否可直接指导高保真布局 | 任一页面信息层级缺失或混乱 |
| 主按钮唯一且位置一致 | 每页是否仅有 1 个主按钮，且位置与触发目标在同类页面保持一致 | 出现多个主按钮抢焦点，或主按钮位置/触发目标不一致 |
| 文案中文化且术语统一 | 是否面向业务用户，是否存在技术字段直出，术语是否统一 | 出现 `from_status`、`to_status`、`biz_id`、`user_id` 等技术字段直出，或术语不一致 |
| 状态颜色和禁用态可辨识 | 状态标签是否定义颜色语义、禁用态、可点击态 | 仅给状态名称，缺失颜色语义/禁用态/可点击态任一项 |
| 表格 / 筛选 / 分页交互闭环 | 列表页是否定义筛选、分页、空态、加载态、失败态、成功态等关键交互反馈 | 任一关键交互缺失，无法形成列表操作闭环 |
| 页面类型与布局模板匹配 | 页面类型（查看/维护/处理）是否与布局模板一致 | 页面类型与布局模板不匹配 |
| 主任务首屏可见 | 首屏是否可见主任务关键区块与关键入口 | 主任务关键区块仅在首屏外可见 |
| 列表页前置重表单限制 | 列表主任务页面是否被大块可编辑表单前置压制 | 出现“上重表单下长列表”且无解耦策略 |
| 主任务跨屏依赖 | 完成主任务是否需跨屏滚动才能触达关键操作 | 关键路径滚动预算未定义或超过 1 屏且无例外说明 |
| 双主流程冲突 | 同页是否并列两个重主流程且主动作冲突 | 同层出现双主流程/双主按钮抢焦点 |
| 工具栏顺序与分页语义 | 是否定义筛选->结果->分页顺序，分页语义是否完整 | 顺序缺失或分页语义元素不全 |
| 筛选后分页重置 | 是否定义筛选后页码重置行为 | 未定义或与主流程矛盾 |

Fail-fast 判定规则：

1. 上述任一门禁项缺失，直接判定为 `🔴 阻塞`
2. 上述门禁项不得降级为 `🟢 建议`
3. 存在任一 Fail-fast 缺失时，评审结论不得为 `通过`

### 步骤 3：问题分类与定级

对每个问题进行分类和定级：

| 级别 | 含义 | 处理要求 |
|---|---|---|
| 🔴 阻塞 | 无法继续设计或开发 | 必须在整改阶段解决 |
| 🟡 重要 | 影响设计质量或有歧义 | 建议在整改阶段解决 |
| 🟢 建议 | 优化建议，不影响核心功能 | 可在后续迭代处理 |

以下情况直接判定为 `🔴 阻塞`：

1. 核心角色未明确
2. 核心主流程未闭环
3. 关键字段缺参数级约束（长度/范围/精度/格式/枚举/空值策略/错误提示）
4. 存在跨字段依赖但未定义联动/互斥/优先级规则
5. 关键状态流转未定义，或状态流转自相矛盾
6. 关键异常场景未定义，或错误处理无法落到用户提示/系统行为
7. 验收标准不可测试，缺少 Given/When/Then（或等价三段式）
8. 非功能需求完全为空，或无任何可验证阈值
9. 业务规则明确影响接口/表结构/测试基线，但未标记影响范围
10. 核心流程缺少伪流程图文本（或等价步骤化流程），导致实现口径不可对齐
11. 存在影响主流程、字段、权限、状态机、接口拆分或表结构设计的未关闭 `【待确认】` / `【冲突】` / 关键 `【设计推断】`
12. `UI可冻结门禁检查清单（Fail-fast）` 任一门禁项不满足（信息层级、主按钮唯一性、文案术语、状态可辨识、表格筛选分页闭环）
13. 页面类型与布局模板不匹配，或未声明页面类型/布局模板
14. 主任务首屏不可见，或关键路径滚动预算未定义
15. 列表页出现前置重表单压制主任务，且无解耦策略
16. 同页双主流程冲突（双主按钮或双主动作链）
17. 工具栏顺序、分页语义、筛选后分页重置规则任一缺失

将所有问题按以下格式写入 `docs/01-requirements/PRD_REVIEW_ISSUES.md`：

### 步骤 5：给出评审结论

| 结论 | 条件 |
|---|---|
| 通过 | Fail-fast 门禁全部通过，且无 🔴 阻塞问题，且无 🟡 重要问题 |
| 有条件通过 | Fail-fast 门禁全部通过，且无 🔴 阻塞问题，有 🟡 重要问题但不影响核心架构 |
| 不通过 | Fail-fast 门禁存在任一未通过，**或**存在 🔴 阻塞问题 |

判定优先级（从高到低）：
1. Fail-fast 门禁任一未通过 → `不通过`（不可降级）
2. 存在 🔴 阻塞问题 → `不通过`
3. 存在 🟡 重要问题但无阻塞 → `有条件通过`
4. 无阻塞且无重要问题 → `通过`

### 步骤 6：提示下一步

评审完成后提示用户：

- 下一步使用 `prd-rectify` 进行 PRD 整改

## Quality Gate（分层）

### P0 Gate（阻塞，最小必检）

- [ ] 步骤 1.5 的 Fail-fast 门禁扫描已执行。
- [ ] 若 Fail-fast 门禁扫描存在任一缺失，评审结论必须为 `不通过`。
- [ ] 存在任一 `🔴 阻塞` 时评审结论必须为 `不通过`。
- [ ] 问题清单中每个阻塞项均有证据与可执行修复建议。
- [ ] Fail-fast 门禁检查结果已输出到 `PRD_REVIEW_ISSUES.md`。

### P1 Coverage Checklist（扩展覆盖）

- [ ] 评审维度覆盖完整（完整性/一致性/明确性/可实现性/可测试性等）。
- [ ] 跨字段规则、状态流转、非功能量化、追溯入口已审查。
- [ ] 问题定级与统计一致，且章节可直接供 `prd-rectify` 消费。

### P2 Reference Checklist（参考）

- [ ] 示例模板与说明文本已更新，且不改变 `P0` 判定口径。

## 术语说明

| 术语 | 含义 | 使用场景 |
|---|---|---|
| 🔴 阻塞 | 评审发现的问题级别，表示无法继续设计或开发，必须在整改阶段解决 | prd-review 问题分级、prd-rectify 问题闭环验证 |
| 阻塞设计 | 待确认事项的类型标记，表示该未决项影响主流程/关键字段/权限/状态机/接口拆分/表结构设计 | prd-compose 待确认事项分类、prd-rectify 冻结判定 |

- `🔴 阻塞` 是评审阶段对已识别问题的严重级别判定
- `阻塞设计` 是编写阶段对未决事项的影响范围标记
- 两者可能重叠：评审发现的某些 `🔴 阻塞` 问题可能源自 `阻塞设计` 标记的待确认项
- 冻结条件：所有 `🔴 阻塞` 问题必须关闭，所有 `阻塞设计` 类型的 `【待确认】` 项必须收敛

## 注意事项

- 评审基于事实，引用 PRD 原文指出问题
- 每个问题必须给出具体修改建议，不能只说“不清楚”
- 不要在评审阶段自行脑补需求，只标记问题
- 对 `状态流转`、`角色-权限-动作矩阵`、`追溯矩阵` 的缺失或失真，需要明确指出对下游 `solution-design`、`qa-design` 的影响
