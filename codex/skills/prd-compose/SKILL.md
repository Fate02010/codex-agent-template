# Skill: prd-compose — 详细需求文档编写

## 触发条件

当 `RESEARCH_SUMMARY.md` 和 `REQUIREMENTS_CLARIFIED.md` 均已生成，需要将需求结构化为正式 PRD 时使用。

## 前置条件

- `docs/00-research/RESEARCH_SUMMARY.md` 已生成（非模板状态）
- `docs/00-research/REQUIREMENTS_CLARIFIED.md` 已生成（非模板状态），其中所有 CQ 问题已有决策结果（或标注为“无待澄清事项”）

## 完成标准

- `docs/01-requirements/PRD_RAW.md` 中每个 `FNNN` 条目都具备完整结构：
  - 所属模块
  - 关联来源 / 关联澄清
  - 用户价值
  - 参与角色
  - 前置条件
  - 触发条件
  - 主流程
  - 替代流程
  - 后置结果
  - 字段清单
  - 业务规则
  - 状态流转（或明确写“无独立状态流转”）
  - 异常场景
  - 边界条件
  - 验收标准
- 每个字段都具备参数级校验约束（按适用项）：
  - 长度/精度
  - 最小值/最大值
  - 格式/正则/枚举
  - 空值策略
  - 错误提示
- 每条验收标准都可直接转化为测试验证动作，禁止空泛描述
- `F` 编号连续无缺，且正文中使用的 `BR-模块-NNN`、`EX-模块-NNN`、`AC-模块-NNN` 编号唯一且可追溯
- `PRD_RAW.md` 已显式区分普通待确认与阻塞设计项，并给出接口、数据、测试的规划入口
- 每个 `FNNN` 都必须包含 `UI约束必填块（强制）`，且完整覆盖页面目标与主任务、主操作唯一性、操作优先级、字段展示映射、文案规范、状态标签规范、反馈规范
- 每个 `FNNN` 都必须定义后台排版约束（页面类型与布局模板匹配、主任务首屏可见、主路径滚动预算、列表/维护解耦策略、工具栏顺序、筛选后分页重置规则）

## 输入

1. `docs/00-research/REQUIREMENTS_CLARIFIED.md` — 需求澄清记录
2. `docs/00-research/RESEARCH_SUMMARY.md` — 调研摘要（补充来源追溯）
3. 可选：设计稿图片（Sketch/Figma 导出图）— 用于补充 UI 相关需求细节
4. `docs/01-requirements/MVP_SCOPE.md`（建议）
5. `docs/01-requirements/OUT_OF_SCOPE.md`（建议）
6. `docs/01-requirements/FEATURE_PRIORITY.md`（建议）
7. `docs/01-requirements/CHANGE_SPLIT_HINTS.md`（建议）

## 输出

- `docs/01-requirements/PRD_RAW.md` — 结构化的初始 PRD

## 执行流程

> 跨阶段传递默认按“章节标题 + 表字段”读取，不依赖章节序号。以下章节序号用于示例，标题语义必须保持一致。

### 步骤 1：读取澄清结果与调研摘要

1. 读取 `REQUIREMENTS_CLARIFIED.md` 获取已确认的功能要点、业务规则、约束和遗留风险
2. 读取 `RESEARCH_SUMMARY.md` 获取原始来源信息，用于追溯标注
3. 若存在 `MVP_SCOPE.md` / `OUT_OF_SCOPE.md` / `FEATURE_PRIORITY.md`，优先以范围结论约束 PRD 编写边界

若当前阶段要求先做范围收敛但未找到范围文档，先回退执行 `scope-definition`。

### 步骤 2：分配正式需求编号

将 `REQUIREMENTS_CLARIFIED.md` 中 `3. 更新后的功能要点` 的功能条目转化为正式编号。若已有范围文档，仅将 In Scope 条目转化为正式需求编号：

1. 按功能模块分组
   - 模块展示统一使用 `EN（中文）`（例如 `MEM（会员管理）`）
   - 模块缩写示例统一使用会员域：`MEM`、`LVL`、`PNT`、`BNF`、`TAG`、`LFC`
2. 分配 F 编号：`F001`、`F002`、…
3. 为每个功能预留业务规则、异常、验收编号段：
   - 业务规则：`BR-MEM-001`
   - 异常场景：`EX-MEM-001`
   - 验收标准：`AC-MEM-001`
4. 建立编号映射表：功能要点编号 → F 编号 → 关联 CQ 编号

| 模块（EN（中文）） | F 编号 | 功能要点 | 关联 CQ |
|---|---|---|---|

补充要求：

1. 若功能存在明确生命周期，必须输出 `状态流转`
2. 若功能不存在独立状态机，必须显式写明“无独立状态流转”，不得留空
3. `业务规则.是否影响接口/表结构` 只用于标注设计影响范围，不要求此阶段给出最终接口或表编号
4. 验收标准必须写成可验证结果，避免“支持正常使用”“体验良好”“系统无异常”等空泛表述
5. 字段校验必须写到参数级，不允许仅写“合法/不合法/按规范校验”
6. `UI约束必填块（强制）` 必须完整填写，不得省略页面目标、主任务、主操作、次操作、危险操作
7. 每个页面仅允许 1 个主按钮，且必须定义主按钮位置与触发目标；同层级不得出现多个主操作抢焦点
8. 按钮优先级必须区分主操作、次操作、危险操作，且危险操作不得与主操作混淆
9. 字段展示必须提供“技术字段 -> 业务中文标签”映射，不得只给技术字段名供 UI 直出
10. 文案必须面向业务用户，术语必须统一且中文化
11. 状态标签必须定义颜色语义、禁用态、可点击态，禁止只给状态名称
12. 反馈规范必须覆盖空态、加载态、失败态、成功态
13. 页面类型与布局模板必须匹配：查看型优先列表主视图，维护型优先表单主视图，处理型优先双栏处理视图
14. 列表页禁止重表单前置压制主列表；如必须同页并存，必须声明解耦策略（弹窗/抽屉/Tab）
15. 主任务首屏可见：必须明确首屏可见信息与关键入口
16. 主任务滚动预算必须量化（默认 <= 1 屏），超出必须写明业务例外与补偿机制
17. 工具栏顺序与分页语义必须明确；分页至少包含总数、当前页、页码、上一页、下一页
18. 筛选后分页是否重置必须明确，默认重置到第 1 页

字段约束强制粒度（每个字段至少覆盖适用项）：

1. 字符串：最小长度、最大长度、字符集/正则、是否允许前后空格、是否大小写敏感
2. 数值：最小值、最大值、精度/小数位、舍入规则（如适用）
3. 枚举：允许值集合、默认值、未知值处理策略
4. 时间：格式、时区、是否允许未来/过去、跨日边界规则（如适用）
5. 空值：空值是否允许、空值时默认行为
6. 错误提示：用户可见提示或错误码口径（供后续接口设计对齐）

信息来源优先级：

1. `REQUIREMENTS_CLARIFIED.md` 中 `3. 更新后的功能要点` 和 `4. 更新后的业务规则与边界`（最高优先）
2. `RESEARCH_SUMMARY.md` 中 `4. 功能要点归纳` 与 `5. 业务规则与约束` 的无争议内容
3. 设计稿中推断的内容（标记 `【设计推断】`）

### 步骤 4：分析设计稿补充 UI 细节

如果用户提供了设计稿图片：

1. 对每张设计稿进行视觉分析
2. 识别页面名称、UI 元素、交互流程、数据字段
3. 将发现的 UI 细节补充到对应 `FNNN` 的字段清单、主流程和页面映射中
4. 从设计稿推断但未在文字需求中明确的内容，标记为 `【设计推断】`
5. 设计稿与澄清后文字有矛盾的，标记为 `【冲突】`
6. 整理设计稿页面清单、关键控件和关键操作

### 步骤 5：编写非功能需求

从 `REQUIREMENTS_CLARIFIED.md` 中提取并结构化：

- 性能要求：响应时间、并发量、数据量
- 安全要求：认证、授权、数据保护
- 可用性与兼容性要求：浏览器、设备、操作系统、无障碍等
- 日志与审计要求：关键操作记录、日志保留、审计字段等

### 步骤 6：编写角色矩阵、页面映射与追溯入口

1. 输出角色定义表，明确角色、核心权限、使用频次和来源
2. 生成 `角色-权限-动作矩阵`，至少覆盖关键操作、数据范围与关联功能
3. 输出 `页面与原型映射`，至少包含页面目标、关联功能、关键控件、关键操作
4. 输出 `追溯矩阵`，为每个 `FNNN` 给出：
   - 来源材料 / 澄清结论
   - 计划接口（允许写候选名称或说明，不要求最终 API 编号）
   - 计划数据表（允许写候选实体或说明，不要求最终表编号）
   - 计划测试（允许写测试主题或说明，不要求最终 TC 编号）

### 步骤 7：编写待确认事项与阻塞标识

整理所有未完全闭环的信息：

1. 普通待确认：不影响当前评审理解，但需要后续澄清
2. 阻塞设计：影响主流程、关键字段、权限边界、状态机、接口拆分、表结构设计的未决项

阻塞设计项必须同时满足：

- 在 `待确认事项` 中将“类型”标记为 `阻塞设计`
- 保留 `【待确认】`、`【设计推断】` 或 `【冲突】` 标识
- 在正文对应位置保留原始标记，供 `prd-review` 消费

### 步骤 9：提示下一步

PRD 编写完成后提示用户：

- 下一步使用 `prd-review` 对 PRD 进行评审

## 注意事项

- **不得杜撰需求**。所有内容必须来自澄清记录或调研摘要，剩余不确定项放入“待确认事项”
- 字段约束必须达到参数级粒度（长度、范围、精度、格式、枚举、空值策略、错误提示），不得只写“按规范校验”
- `UI约束必填块（强制）` 缺失任一项时，`PRD_RAW.md` 不满足评审输入条件
- F 编号必须唯一且连续，正文中的 `BR-*`、`EX-*`、`AC-*` 编号不得重复
- 模块展示字段统一使用 `EN（中文）`，编号中的模块段仍仅使用英文缩写
- Out of Scope 能力不得写入 PRD 功能正文
- 追溯链：源材料 → `RESEARCH_SUMMARY.md` → `REQUIREMENTS_CLARIFIED.md`（`CQ-xxx`）→ `PRD_RAW.md`（`Fxxx`）
- 保留 `【设计推断】` 和 `【冲突】` 标记，供下游 `prd-review` 消费
- 标记为“阻塞设计”的条目未关闭前，`PRD_RAW.md` 只能进入评审，不得被视为可直接进入 `solution-design` 的成熟输入
- 输出的 `PRD_RAW.md` 结构已接近 `PRD_RECTIFIED.md`，但仍需经过 `prd-review` 和 `prd-rectify` 正式冻结
- 设计稿分析使用 Agent 的视觉能力，非外部脚本
