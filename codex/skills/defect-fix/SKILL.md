# Skill: defect-fix — 缺陷修复闭环

## 触发条件

当测试执行发现失败用例（`TEST_REPORT.md` 中存在失败记录），或用户手动报告缺陷时使用。

## 输入

1. `docs/04-testing/TEST_REPORT.md` — 失败用例和失败分析
2. `docs/04-testing/TEST_CASES.md` — 完整测试用例详情
3. `docs/01-requirements/PRD_RECTIFIED.md` — 需求基线
4. `docs/03-architecture/API_CONTRACT.md` — 接口契约
5. `docs/03-architecture/DATA_MODEL.md` — 数据模型
6. `docs/03-architecture/ARCHITECTURE.md` — 架构设计（第 11 节序列图用于核对根因分析时的调用链是否符合设计意图）
7. `backend/` 和 `frontend/` 下的相关源代码

## 输出

1. `docs/04-testing/DEFECT_LOG.md` — 缺陷记录（新建或追加）
2. 修复后的源代码
3. 更新后的文档（如修复涉及设计变更）
4. 回归测试结果追加到 `TEST_REPORT.md`

## 执行流程

### 步骤 1：读取失败上下文

1. 按章节标题读取 `TEST_REPORT.md` 中“失败与阻塞明细”（或等价失败用例章节）
2. 对每个失败用例，从 `TEST_CASES.md` 中读取完整用例信息
3. 读取关联需求（FXXX）对应的 `PRD_RECTIFIED.md` 章节
4. 读取关联接口（API-XXX-NNN）对应的 `API_CONTRACT.md` 章节

### 步骤 2：登记缺陷

对每个失败，在 `docs/04-testing/DEFECT_LOG.md` 中创建或追加缺陷记录：

- 若 `DEFECT_LOG.md` 不存在，先创建最小台账结构（文档信息、缺陷明细、变更记录），状态设为`草稿`
- 若 `DEFECT_LOG.md` 仍为模板，先补全文档信息（文档类型/生成 Skill/上游输入/版本/日期/状态）并将状态更新为`草稿`
- 缺陷记录统一写入 `2. 缺陷明细` 章节，避免散落到非标准位置

`DEFECT_LOG.md` 最小结构：

```markdown
# 缺陷记录

## 文档信息
- 文档类型：产物
- 生成 Skill：`defect-fix`
- 上游输入：`TEST_REPORT.md`、`TEST_CASES.md`
- 版本：vX.Y
- 日期：YYYY-MM-DD
- 状态：草稿

## 1. 统计

## 2. 缺陷明细

## 变更记录
| 版本 | 日期 | 说明 |
|---|---|---|
```

```markdown
## BUG-[模块]-[NNN]: [缺陷标题]

- **关联用例**：TC-XXX-NNN
- **关联需求**：FXXX
- **关联接口**：API-XXX-NNN
- **严重程度**：致命 / 严重 / 一般 / 轻微
- **状态**：新建
- **发现日期**：YYYY-MM-DD

### 复现步骤
（从测试用例步骤复制）

### 预期结果
（从测试用例复制）

### 实际结果
（从测试报告复制）

### 根因分析
（见步骤 3 分析结果）

### 修复方案
（文档优先：需要哪些文档/代码变更）
```

缺陷编号格式严格遵循 `tests/AGENTS.md` 的“缺陷记录规则”：`BUG-模块-序号`。

### 步骤 3：根因分析

对每个缺陷执行：

1. **追踪代码路径**：从 Controller → Application Service → Domain Service → Repository，定位问题代码，并与 `ARCHITECTURE.md` 第 11 节序列图对照；若调用链与序列图存在偏差，先判断偏差是代码实现问题还是设计问题，再决定修复路径
2. **对比接口契约**：将实际行为与 `API_CONTRACT.md` 中定义的接口规格对比
3. **检查数据模型**：确认实体/PO 是否与 `DATA_MODEL.md` 一致
4. **定位具体原因**：记录具体的代码位置和逻辑错误
5. **写入 DEFECT_LOG.md** 的"根因分析"章节

### 步骤 4：文档优先修复

**如果缺陷暴露了设计问题**（接口定义错误、数据模型缺陷、需求遗漏）：

1. **先更新相关文档**（`API_CONTRACT.md`、`DATA_MODEL.md` 或 `PRD_RECTIFIED.md`）
2. 使用【修改】标记标注变更内容
3. 更新文档的变更记录
4. 然后再进行代码修复

**如果缺陷是纯代码 Bug**（设计正确，实现有误）：

1. 跳过文档更新
2. 直接进行代码修复

### 步骤 5：代码修复

1. 按照 `backend/AGENTS.md` 或 `frontend/AGENTS.md` 的规范修复代码
2. 确保修复针对根因，而非仅仅应付症状
3. 遵循 DDD 分层约束
4. 为修复的代码路径添加或更新单元测试

### 步骤 6：回归测试

1. 重新运行失败的测试用例
2. 同时运行所有 P0 测试用例，检查是否引入新问题
3. 记录回归结果

### 步骤 7：更新缺陷状态

在 `DEFECT_LOG.md` 中更新每个已修复的缺陷：

| 字段 | 更新内容 |
|---|---|
| 状态 | 新建 → 已修复 → 已验证（回归通过后） |
| 修复日期 | YYYY-MM-DD |
| 回归结果 | 通过 / 失败 |

补充回归用例标记：`[回归] TC-XXX-NNN-R1`（遵循 `tests/AGENTS.md` 的“回归要求”）。

### 步骤 8：追加回归轮次到 TEST_REPORT.md

在 `TEST_REPORT.md` 末尾追加回归轮次章节：

```markdown
## 回归轮次 [N] — YYYY-MM-DD

| 缺陷编号 | 关联用例 | 回归结果 | P0 回归 |
|---|---|---|---|
| BUG-XXX-001 | TC-XXX-NNN | 通过/失败 | 全部通过 / N 个失败 |

### 回归结论
- 本轮修复 N 个缺陷，回归通过 N 个
- P0 用例全部通过：是/否
- 是否需要下一轮修复：是/否
```

### 步骤 9：循环或完成

- **如果所有缺陷已验证且 P0 回归通过**：修复完成，提示用户质量门禁已达标
- **如果发现新的失败**：回到步骤 2，处理新的失败
- **最多 3 轮迭代**，超过 3 轮后上报用户决策，并给出以下选项：
  1. 若根因为设计缺陷（接口定义错误、序列图流程错误、数据模型缺陷）→ 回退 `architecture-rectify` 重新整改设计基线
  2. 若根因为复杂实现问题且设计无误 → 由用户授权后继续第 4 轮修复

### 步骤 10：文档同步检查

所有修复验证完成后：

1. 确保所有文档变更已记录在各文档的变更记录中
2. 建议运行 `doc-check` 验证追溯链完整性

## 注意事项

- **最多 3 轮修复-回归迭代**，防止无限循环
- **文档优先原则**：如果是设计错误，必须先改文档再改代码
- 每个缺陷必须有唯一的 `BUG-[模块]-[NNN]` 编号
- 回归必须包含**所有 P0 用例**，不仅仅是修复的用例
- 缺陷状态必须经过回归测试验证后才能标记为"已验证"
- 修复代码必须遵循对应 `AGENTS.md` 中的所有规范约束
