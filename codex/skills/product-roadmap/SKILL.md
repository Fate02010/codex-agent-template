# Skill: product-roadmap — 产品路线图规划

## Purpose

基于业务目标、需求输入、当前产品状态、版本规划和约束条件，产出结构化产品路线图（roadmap）与阶段规划文档。

本 Skill 的核心目标：

- 规划产品 0→1 或 1→N 的阶段路线图。
- 输出版本阶段划分、里程碑、能力包、优先级和依赖关系。
- 将候选能力收敛为按阶段推进的产品路线图。
- 支持季度路线图、版本路线图、MVP→V2→V3 规划。
- 为后续 `change-intake`、`scope-definition`、`iteration-plan`、资源安排提供输入。

本 Skill 聚焦“产品规划能力”，不替代 PRD、架构设计、项目执行管理或代码实现。

## When to Use

满足以下任一条件时触发：

- 已完成业务调研，需要把候选能力转成中长期产品路线图。
- 需要规划产品从 MVP 到后续版本的阶段演进。
- 需要做季度规划、半年度规划或版本阶段规划。
- 需要明确“当前已交付能力 / 本期规划能力 / 后续候选能力”的阶段边界。
- 需要给后续 `scope-definition`、`change-intake`、`iteration-plan` 提供更上层的产品规划输入。

默认阶段表达规则：

- 未显式指定时间窗口时，优先使用 `MVP / V1 / V2 / V3`。
- 若输入中明确给出季度或时间窗口，则可改用 `Q1 / Q2 / Q3 / Q4` 或等价时间阶段。

## When Not to Use

以下场景不应使用本 Skill：

- 需要编写完整 PRD（使用 `prd-compose` / `prd-rectify`）。
- 需要收敛“本期 MVP 范围边界”而非多阶段路线图（使用 `scope-definition`）。
- 需要决定“本轮迭代纳入哪些 CR”并冻结版本（使用 `iteration-plan`）。
- 需要做技术架构设计、接口设计、数据模型设计（使用 `solution-design`）。
- 需要直接实现代码（使用 `dev-implement`）。
- 需要输出 UI 设计说明、原型或设计基线（使用 `ui-design-spec` / `prototype-build`）。
- 需要写纯营销式产品愿景文案，而非可执行路线图。

## Inputs

按优先顺序读取：

1. `docs/00-research/RESEARCH_SUMMARY.md`
2. `docs/00-research/REQUIREMENTS_CLARIFIED.md`
3. `docs/01-requirements/MVP_SCOPE.md`（如存在）
4. `docs/01-requirements/OUT_OF_SCOPE.md`（如存在）
5. `docs/01-requirements/FEATURE_PRIORITY.md`（如存在）
6. `docs/01-requirements/CAPABILITY_CANDIDATES.md`（如存在）
7. `openspec/project.md`（如存在）
8. 当前版本基线 / 当前已交付能力清单（如 `docs/04-iteration/RELEASE_BASELINE.md`、既有发布记录、历史路线图）
9. 业务目标、资源约束、时间窗口、依赖信息（如输入材料中存在）

输入降级策略：

- 缺少 `CAPABILITY_CANDIDATES.md` 时，从调研与澄清文档中提取候选能力，并登记来源。
- 缺少当前版本基线时，路线图中必须显式标记“当前能力现状不完整”为 `【待确认】`。
- 缺少资源约束或时间窗口时，仍可输出版本式路线图，但必须标注约束风险。

## Outputs

必须输出以下文件：

1. `docs/04-iteration/PRODUCT_ROADMAP.md`
2. `docs/04-iteration/ROADMAP_PHASES.md`
3. `docs/04-iteration/ROADMAP_DEPENDENCIES.md`
4. `docs/04-iteration/ROADMAP_RISKS.md`

输出边界：

- 本 Skill 只输出产品路线图与阶段规划文档。
- 不写完整 PRD、架构设计、UI 设计、任务排期明细或代码实现方案。
- 路线图可为后续阶段提供输入，但不直接替代 `scope-definition` 或 `iteration-plan`。

## Rules

执行时必须遵守：

1. 路线图必须基于业务目标、范围边界和当前能力现状推导。
2. 必须明确阶段划分，例如：`MVP / V1 / V2 / V3` 或 `Q1 / Q2 / Q3 / Q4`。
3. 每个阶段都必须写清：
   - 阶段目标
   - 核心能力
   - 不纳入内容
   - 依赖关系
   - 风险
   - 完成判定
4. 必须区分：
   - 当前已交付能力
   - 本期规划能力
   - 后续候选能力
5. 必须说明优先级依据，优先级不得仅凭主观偏好决定。
6. 若信息不足，必须标记 `【待确认】` 并说明影响。
7. 若基于上下文做合理推断，必须标记 `【推断】` 并说明依据。
8. 不得输出脱离当前项目现实约束的理想化 roadmap。
9. 不得把 roadmap 写成 PRD 细节文档。
10. 不得把未来所有能力都堆进最近一个阶段。
11. 阶段规划必须兼顾业务价值、依赖顺序、资源约束和交付风险。
12. 路线图中的阶段边界必须能直接供后续 `scope-definition`、`change-intake`、`iteration-plan` 消费。

## Workflow

### 步骤 1：理解当前业务目标与项目边界

- 提取业务目标、核心用户、关键场景、成功标准、资源与时间约束。
- 读取 `MVP_SCOPE.md` / `OUT_OF_SCOPE.md` / `FEATURE_PRIORITY.md`（如有），识别已有范围边界。
- 识别哪些约束是现实约束，哪些只是愿景陈述。

### 步骤 2：识别候选能力池

- 汇总 `RESEARCH_SUMMARY.md`、`REQUIREMENTS_CLARIFIED.md`、`CAPABILITY_CANDIDATES.md`、`project.md` 中的能力项。
- 合并同义能力，拆分混合能力，形成统一候选能力池。
- 为每个能力登记来源与业务价值线索。

### 步骤 3：判断当前能力现状与缺口

- 读取当前版本基线或已交付能力清单，识别“已经有 / 本轮缺 / 后续候选”。
- 若缺少可靠现状输入，必须在输出中标记 `【待确认】`。
- 输出能力现状视图：已交付能力、能力缺口、潜在扩展能力。

### 步骤 4：进行阶段划分

- 基于业务目标、优先级、依赖关系、交付风险和资源约束，划分路线图阶段。
- 默认优先使用版本阶段（如 `MVP / V1 / V2 / V3`）。
- 仅当输入明确要求时间维度时，才采用季度阶段（如 `Q1 / Q2 / Q3 / Q4`）。
- 每个阶段只纳入在当前阶段可解释、可交付、依赖可落地的能力包。

### 步骤 5：定义每阶段目标、能力包、依赖、风险和完成标准

- 为每个阶段定义：
  - 阶段目标
  - 核心能力包
  - 阶段非目标
  - 阶段依赖
  - 风险与约束
  - 完成判定
- 明确阶段之间“为什么这样拆分”。

### 步骤 6：输出路线图主文档

- 在 `PRODUCT_ROADMAP.md` 中输出：
  - 路线图概览
  - 当前能力现状
  - 阶段总览
  - 优先级依据
  - 总体取舍理由

### 步骤 7：输出阶段说明、依赖与风险文档

- 在 `ROADMAP_PHASES.md` 中逐阶段展开详细说明。
- 在 `ROADMAP_DEPENDENCIES.md` 中输出阶段依赖、能力包依赖、外部依赖和顺序依赖。
- 在 `ROADMAP_RISKS.md` 中输出路线图级与阶段级风险、缓解策略、待确认问题。

### 步骤 8：标记待确认与推断

- 单独列出 `【待确认】`，说明不确认将影响哪个阶段判断。
- 单独列出 `【推断】`，说明依据和潜在偏差。

## Quality Gate

完成前必须全部满足：

- [ ] 路线图可解释“为什么这样分阶段”。
- [ ] 阶段之间有明确边界，不存在职责与能力重叠混乱。
- [ ] 每个阶段都能回答“做什么 / 不做什么 / 为什么”。
- [ ] 路线图与 `MVP_SCOPE.md`、`OUT_OF_SCOPE.md`、`FEATURE_PRIORITY.md` 一致（如这些文档存在）。
- [ ] 已明确区分当前已交付能力、本期规划能力、后续候选能力。
- [ ] 已输出优先级依据，而非笼统主观排序。
- [ ] 不存在明显范围跳跃或依赖冲突。
- [ ] `【待确认】` 和 `【推断】` 已显式标记并附影响说明。
- [ ] 输出能直接供后续 `scope-definition`、`change-intake`、`iteration-plan` 使用。

## Example

示例主题：会员管理系统

### 示例输入

- 候选能力：会员档案、等级成长、积分、权益、标签、生命周期
- 业务目标：先形成会员主数据运营闭环，再逐步提升运营分层能力
- 现实约束：
  - 首期团队规模有限
  - 生命周期自动化规则尚未冻结
  - 权益发放依赖外部订单与库存口径

### 示例输出思路

1. 当前已交付能力
- 无正式系统，只有线下 Excel 会员台账与人工分层规则。

2. `MVP` 阶段
- 阶段目标：形成统一会员主数据与基础运营查询闭环。
- 核心能力：
  - 会员档案
  - 等级成长基础规则
  - 积分账户与积分流水查询
- 不纳入内容：
  - 权益自动发放
  - 生命周期自动触达
  - 标签自动计算
- 依赖：
  - 会员主数据口径统一
  - 积分字段定义明确
- 风险：
  - 积分规则若未冻结，会影响等级与流水展示
- 完成判定：
  - 会员可查询、可维护、可查看等级与积分变化

3. `V2` 阶段
- 阶段目标：从基础会员管理升级到可分层运营。
- 核心能力：
  - 手工标签
  - 权益配置
  - 权益发放记录
- 不纳入内容：
  - 自动化生命周期编排
  - 多渠道触达
- 依赖：
  - `MVP` 阶段会员与等级口径稳定
  - 权益规则与外部业务规则对齐
- 风险：
  - 权益口径若依赖订单系统，联动成本上升

4. `V3` 阶段
- 阶段目标：建设自动化运营与生命周期管理能力。
- 核心能力：
  - 生命周期分层
  - 标签自动计算
  - 自动化触达策略
- 不纳入内容：
  - 复杂 AI 推荐与实时个性化运营
- 依赖：
  - `V2` 的标签、权益、会员行为数据沉淀
- 风险：
  - 生命周期规则可能存在较多 `【待确认】`
  - 自动触达能力依赖外部渠道接入

5. 优先级依据
- 优先建设“会员主数据 + 等级 + 积分”，因为这是后续标签、权益、生命周期的共同基础。
- 权益与标签放在 `V2`，因为需要在基础口径稳定后再上。
- 生命周期放在 `V3`，因为规则复杂、依赖多、风险高，不适合挤进最近阶段。

6. 标记示例
- 若“积分是否过期”未冻结，应标记为 `【待确认】`。
- 若“生命周期先按沉默/活跃/流失三段划分”来自业务经验而非正式规则，应标记为 `【推断】`。
