# Skill: code-review — 代码评审

## Purpose

对本次代码变更执行工程化差异评审，识别缺陷风险、回归风险与合并风险，并基于需求、设计、接口、数据模型、测试基线给出可执行评审结论与门禁建议。

本 Skill 的目标：

- 输出可落地的问题清单（含证据、影响与修复建议）。
- 建立“需求-实现-测试”追溯，定位变更偏差与遗漏。
- 对是否允许合并给出明确结论：`PASS` / `PASS WITH WAIVER` / `REJECT`。

## When to Use

满足以下任一条件时触发：

- 需要评审一个明确变更集（`git diff` / MR / PR / commit range）。
- 需要判断本次变更是否满足合并门禁。
- 需要基于需求与设计基线做实现差异审查。
- 需要输出结构化评审报告，供研发、测试、产品共同决策。

## When Not to Use

以下场景不得使用本 Skill 替代其他阶段：

- 编写完整 PRD（使用 `prd-compose` / `prd-rectify`）。
- 产出架构设计方案（使用 `solution-design`）。
- 直接实现业务代码（仅当用户明确要求“边审边改”时例外）。
- 无边界全仓巡检（默认只审本次变更及直接影响范围）。
- 纯样式偏好讨论（无风险价值的 nit 不作为阻塞项）。
- 替代测试执行或性能压测（使用 `qa-execute` 或专项性能流程）。

## Inputs

按以下优先顺序读取输入：

1. 本次变更证据：
   - `git diff` / 变更文件列表 / diff stat
2. 需求基线：
   - `docs/01-requirements/PRD_RECTIFIED.md`
3. 设计与契约基线：
   - `docs/03-architecture/ARCHITECTURE.md`
   - `docs/03-architecture/API_CONTRACT.md`
   - `docs/03-architecture/DATA_MODEL.md`
4. 测试基线与结果：
   - `docs/04-testing/TEST_CASES.md`
   - 相关测试结果（如有）
5. OpenSpec 工件（如项目启用）：
   - current change artifact

输入降级规则：

- 缺失任一关键基线文档时，继续评审代码证据，但必须在结果中标注 `【待确认】` 并说明影响范围。
- 对无法直接证明的结论，必须标注 `【推断】` 并写明依据。

## Outputs

必须输出以下文件：

1. `docs/04-testing/CODE_REVIEW_REPORT.md`
2. `docs/04-testing/CODE_REVIEW_ISSUES.md`

输出要求：

- `CODE_REVIEW_ISSUES.md`：问题明细与证据，按 `P0 > P1 > P2 > P3` 排序。
- `CODE_REVIEW_REPORT.md`：门禁结论、风险摘要、修复优先级与建议补测项。
- 结论展示顺序必须为“先结论后摘要”，并在内容组织上“先问题后概述”。

## Rules

执行时必须遵守：

1. 默认只评审本次变更及其直接影响范围，不做无边界扩审。
2. 问题必须按严重级别排序：`P0 > P1 > P2 > P3`。
3. 每条问题必须包含以下字段，不可缺漏：
   - 问题编号
   - 级别（P0/P1/P2/P3）
   - 文件路径 + 行号
   - 问题类型
   - 问题描述
   - 影响
   - 触发条件/复现方式
   - 修复建议
   - 是否阻塞合并
4. 重点审查维度必须覆盖：
   - 正确性
   - 安全
   - 数据一致性
   - 并发
   - 事务边界
   - 接口兼容性
   - 性能
   - 可观测性
   - 测试覆盖缺口
5. 无法确认的信息必须标注 `【待确认】`。
6. 基于上下文推断的结论必须标注 `【推断】`。
7. 若无阻塞问题，必须明确写出“未发现阻塞性问题”，并补充剩余风险与建议补测项。
8. 禁止输出无法定位到代码位置（文件与行号）的笼统结论。
9. 禁止将纯风格问题升级为 `P0/P1`。
10. 结论与级别必须一致：阻塞问题存在时不得给出 `PASS`。
11. 冷启动规则（强制）：
   - 若目标目录不存在，先创建目录。
   - 若 `CODE_REVIEW_REPORT.md` 或 `CODE_REVIEW_ISSUES.md` 不存在，按本 Skill 内置结构创建完整文档。
   - 若文档状态为 `模板`，整文件覆盖为正式产物结构。
   - 若文档状态不为 `模板`，按章节标题增量更新，不按章节序号硬编码。

### 步骤 1：建立评审边界与追溯映射

- 锁定评审对象：commit range / diff 文件集 / 直接影响模块。
- 读取需求、设计、接口、数据、测试基线，建立“需求-实现-测试”追溯关系。

### 步骤 2：按固定顺序执行审查

按以下顺序检查，避免遗漏关键风险：

1. 正确性
2. 数据一致性
3. 安全
4. 接口兼容性
5. 并发
6. 性能
7. 可观测性
8. 测试覆盖

### 步骤 3：逐文件记录证据

- 逐文件记录问题证据：路径、行号、上下文、触发条件。
- 对不可复现但高风险的项，标注 `【待确认】` 并明确验证动作。

### 步骤 4：生成问题清单

- 产出 `CODE_REVIEW_ISSUES.md`。
- 按严重级别分组并排序，每条问题具备完整字段。

### 步骤 5：生成评审结论

- 产出 `CODE_REVIEW_REPORT.md`。
- 先给门禁结论，再给摘要与统计。
- 给出最小修复优先级建议：先修 `P0/P1`，再评估 `P2/P3`。

## Quality Gate

完成前必须全部满足：

- [ ] `P0/P1` 问题均可复现或具备明确证据链。
- [ ] 每个结论都能追溯到文件与行号。
- [ ] 门禁结论与问题级别一致，不自相矛盾。
- [ ] `REJECT`：存在 `P0` 或未缓解的 `P1`。
- [ ] `PASS WITH WAIVER`：无 `P0`，`P1` 已接受风险或仅有 `P2/P3`。
- [ ] `PASS`：无 `P0/P1`，且无阻塞合并问题。
- [ ] 若结论非 `PASS`，已给出可执行修复优先级和补测建议。

## Example

示例主题：会员管理系统

### 示例输入

- 变更范围：用户（User，用户）、会员等级（Membership Level，会员等级）、积分（Points，积分）、权益（Benefits，权益）、订单（Order，订单）相关代码。
- 基线文档：
  - `PRD_RECTIFIED.md`
  - `ARCHITECTURE.md`
  - `API_CONTRACT.md`
  - `DATA_MODEL.md`
  - `TEST_CASES.md`
- 附加证据：MR diff + 单测结果 + API 回归结果。

### 示例输出思路

#### A. `docs/04-testing/CODE_REVIEW_ISSUES.md`

1) `CRI-001`（P1，阻塞）
- 文件位置：`backend/member-admin-service/src/main/java/.../PointsService.java:142`
- 问题类型：数据一致性 / 事务边界
- 问题描述：积分扣减与订单状态更新不在同一事务，订单取消重试时可能出现“订单失败但积分已扣”。
- 影响：积分账实不一致，导致会员权益误判。
- 触发方式：订单服务调用超时重试 + 并发取消场景。
- 修复建议：将积分变更与订单状态迁移纳入同一事务边界；增加幂等键与回滚校验。
- 是否阻塞合并：是

2) `CRI-002`（P2，非阻塞）
- 文件位置：`frontend/member-web/src/api/member.ts:88`
- 问题类型：接口兼容性 / 可观测性
- 问题描述：前端仍按旧字段 `levelName` 读取，后端契约已调整为 `memberLevelName`，仅在异常分支打印通用日志。
- 影响：部分页面等级字段显示为空，且定位成本高。
- 触发方式：会员列表接口返回新字段结构时。
- 修复建议：按 `API_CONTRACT` 更新字段映射；补充结构化日志（接口名、请求ID、字段缺失详情）。
- 是否阻塞合并：否

> 若“积分过期策略”在需求文档中未冻结，需在问题中标注 `【待确认】`。
> 若“重试窗口 5 秒”来自历史经验而非基线文档，需标注 `【推断】`。

#### B. `docs/04-testing/CODE_REVIEW_REPORT.md`

- 门禁结论：`REJECT`（存在未缓解 `P1`）
- 结论优先展示：
  - 是否允许合并：否
  - 阻塞项数量：`P1 x 1`
  - 非阻塞项数量：`P2 x 1`
- 摘要说明（后置）：
  - 本次评审覆盖会员与订单积分链路，发现事务一致性风险为主要阻塞项。
  - 建议先修 `CRI-001` 并补测“并发取消 + 重试”场景后复审。
  - 当前无 `P0`，但存在可见性与兼容性改进项。

当仅有 `P2/P3` 且无阻塞合并问题时：

- 明确写出“未发现阻塞性问题”。
- 结论可为 `PASS WITH WAIVER` 或 `PASS`（依剩余风险判断）。

## 断点恢复

> 通用恢复原则见根目录 `AGENTS.md` § 14。本章节声明本 Skill 的步骤级检查点；未列出的项回退到 `AGENTS.md` § 14.4 默认规则。

### 检查点表格

| 步骤 | 步骤名称 | 完成判定条件 | 续执起点 |
|---|---|---|---|
| 步骤 0 | 初始化输出载体 | `docs/04-testing/CODE_REVIEW_ISSUES.md` 和 `CODE_REVIEW_REPORT.md` 均存在且非模板 | 步骤 1 |
| 步骤 1 | 建立评审边界与追溯映射 | `CODE_REVIEW_ISSUES.md` 中存在追溯映射表内容 | 步骤 2 |
| 步骤 2 | 按固定顺序执行审查 | `CODE_REVIEW_ISSUES.md` 中存在至少一条问题记录 | 步骤 3 |
| 步骤 3 | 逐文件记录证据 | `CODE_REVIEW_ISSUES.md` 问题记录包含文件路径与证据字段 | 步骤 4 |
| 步骤 4 | 生成问题清单 | `CODE_REVIEW_ISSUES.md` 状态字段不为模板且问题按 P0>P1>P2>P3 排序 | 步骤 5 |
| 步骤 5 | 生成评审结论 | `CODE_REVIEW_REPORT.md` 存在且门禁结论字段有值 | — |

### 默认恢复原则（兜底）

1. 若所有输出文件均不存在，从步骤 0 全量执行。
2. 若部分文件存在，从最早未完成步骤续执，已有内容按增量更新处理。
3. Gate Report 结论为 `BLOCKED` 时，从步骤 0 重新评估（参见 `AGENTS.md` § 14.5 第 4 条）。
