# Skill: prd-rectify — PRD 整改

## 触发条件

当 PRD 评审完成（`PRD_REVIEW_ISSUES.md` 已生成），需要输出整改版需求文档时使用。

## 输入

1. `docs/01-requirements/PRD_REVIEW_ISSUES.md` — 评审问题清单
2. `docs/01-requirements/PRD_RAW.md` — 原始 PRD 文档

## 输出

- `docs/01-requirements/PRD_RECTIFIED.md` — 整改后的需求文档
- `docs/01-requirements/PRD_RECTIFIED_GATE_REPORT.md` — 冻结前强制门禁报告

## 执行层级导读（Progressive Disclosure）

- `P0 必检（阻塞）`：阻塞/重要问题闭环、参数级约束补齐、冻结前置条件可判定。
- `P1 扩展（覆盖）`：追溯矩阵、非功能细化、风险与待确认治理完整。
- `P2 参考（说明）`：示例与说明文本仅作参考，不参与放行。
- 执行顺序必须为：先过 `P0 Gate`，再进入 `P1`；`P2` 不得覆盖 `P0` 结论。

## 执行规则

1. 冷启动规则（强制）：
   - 若目标目录不存在，先创建目录。
   - 若目标文件不存在，按本 Skill 内置结构创建完整文档。
   - 若目标文件状态为 `模板`，整文件覆盖为正式产物结构。
   - 若目标文件状态不为 `模板`，按章节标题增量更新，不按章节序号硬编码。
2. 整改必须仅针对评审问题和其直接关联项，不得扩展需求范围。
3. 对无法确认的内容必须标记 `【待确认】`，不得自行拍板。
4. `P0 Gate` 未通过时，文档状态不得更新为 `已冻结`。
5. 规则去重：`执行规则/步骤 3` 保留主定义，后续检查清单仅引用编号与结论。
6. 冻结前必须执行自动化门禁：
   - `scripts/run_prd_gate.sh --mode rectify --repo-root "$PWD"`
   - 任一失败时文档状态只能为 `已整改`，不得置为 `已冻结`。

## 执行流程

### 步骤 0：P0 Gate（阻塞）

1. 校验 `PRD_REVIEW_ISSUES.md` 与 `PRD_RAW.md` 可读。
2. 校验阻塞项与重要项可定位到具体条目。
3. 任一不满足时输出 `BLOCKED/FAIL` 并停止，不进入步骤 1~7。

### 步骤 1：读取输入

1. 读取 `docs/01-requirements/PRD_REVIEW_ISSUES.md`，提取所有 🔴 阻塞和 🟡 重要问题
2. 读取 `docs/01-requirements/PRD_RAW.md`
3. 按章节映射整理 `PRD_RAW.md` 的关键上游结构：
   - `所属模块`
   - `状态流转`
   - `业务规则` 中的“影响接口”与“影响表结构”
   - `角色-权限-动作矩阵`
   - `追溯矩阵`

### 步骤 2：逐项整改

针对每个阻塞和重要问题：

1. 找到 PRD 中对应的内容
2. 按评审建议进行修改
3. 使用标记标注变更：`【新增】`、`【修改】`、`【待确认】`
4. 若问题涉及接口或数据设计前提，必须同步修正：
   - `业务规则.影响接口` / `业务规则.影响表结构`
   - `状态流转`
   - `追溯矩阵`

### 步骤 3：补全缺失内容

**前置：基线对齐检查（强制）**

在逐项整改之前，先对 PRD_RAW.md 的表格格式进行基线对齐，确保后续整改基于正确的结构：

1. **字段清单表格列对齐**：检查每个 FNNN 的字段清单是否为标准 9 列格式（`字段名|类型|长度/精度|必填|默认值|校验规则|空值策略|错误提示|说明`）。若为 6 列旧格式，先补齐缺失的 3 列（长度/精度、空值策略、错误提示），再进行内容整改
2. **异常场景表格列对齐**：检查每个 FNNN 的异常场景表是否为标准 5 列格式（`编号|场景|处理方式|用户提示|恢复动作`）。若为 4 列旧格式，先补齐 `恢复动作` 列
3. **验收标准表格列对齐**：检查每个 FNNN 的验收标准表是否为标准 5 列 Given-When-Then 格式（`编号|验收项|前置条件(Given)|操作步骤(When)|预期结果(Then)`）。若为 3 列旧格式，先转换为新格式
4. **业务规则表格列对齐**：检查是否将 `影响接口` 和 `影响表结构` 拆分为独立两列
5. **UI约束必填块存在性**：检查每个 FNNN 是否包含 UI 约束必填块章节，缺失的先创建完整骨架

基线对齐完成后，再按下方清单逐项补全内容。

检查并补全以下内容：

| 检查项 | 要求 |
|---|---|
| 功能编号 | 每个功能点必须有唯一编号（`F001`、`F002`…） |
| 角色定义 | 明确系统涉及的所有角色及权限 |
| 角色-权限-动作矩阵 | 核心角色、关键动作、数据范围和关联功能完整 |
| 业务流程 | 核心流程用文字或伪流程图描述 |
| 字段清单 | 每个表单/页面的字段必须包含类型、长度/精度、必填、默认值、最小/最大、格式/枚举、空值策略、错误提示 |
| 业务规则 | 所有业务判断逻辑必须量化和明确，并标记影响接口与影响表结构 |
| 状态流转 | 有生命周期的功能必须定义状态机；无生命周期的功能需明确“无独立状态流转” |
| 异常场景 | 每个功能点的异常流和错误提示 |
| 边界条件 | 数值范围、字符长度、数量上限等 |
| 模块展示 | 所属模块必须使用 `EN（中文）`（如 `MEM（会员管理）`） |
| 非功能需求 | 性能指标、安全要求、兼容性要求 |
| UI约束必填块（强制） | 每个功能点必须补齐页面目标与主任务、页面类型（查看型/维护型/处理型）、主操作唯一性、操作优先级、字段展示映射、文案规范、状态标签规范、反馈规范 |
| 后台排版约束（强制） | 每个功能点必须补齐布局模板、主任务首屏可见、主路径滚动预算、列表/维护解耦策略、工具栏顺序、筛选后分页重置规则 |
| 追溯入口 | 每个功能点都能映射到计划接口、计划数据表、计划测试 |
| 验收标准 | 每条验收标准必须使用 Given-When-Then（前置条件/操作步骤/预期结果）格式，禁止空泛表述；每个功能不少于 3 条，且覆盖正常流程、异常流程、边界条件 |
| 异常场景分类覆盖 | 每个功能点必须覆盖 5 类异常（输入校验/业务逻辑/权限/系统/并发），含恢复动作 |
| 边界条件覆盖 | 每个功能点至少 3 个边界条件，覆盖输入长度/数量/时间/并发 |
| 验收标准格式 | 使用 Given-When-Then 5 列格式，每功能不少于 3 条 |
| 模糊词清除 | PRD 正文不含"等"/"相关"/"其他"/"若干"/"部分" |
| 后置结果完整性 | 不使用模糊词，列出完整的字段/状态变化清单 |

字段约束必填规则（每个字段按适用项补齐）：

1. 字符串：最小长度、最大长度、字符集/正则、前后空格策略
2. 数值：最小值、最大值、精度/小数位、溢出处理
3. 枚举：允许值集合、默认值、未知值处理
4. 时间：格式、时区、未来/过去时间限制
5. 空值：空值是否允许、空值默认行为
6. 错误提示：用户提示文案或错误码口径

UI约束必填规则（每个功能点必须补齐）：

1. 页面目标与主任务：必须同时定义页面目标与主任务，且必须明确页面类型（查看型页面 / 维护型页面 / 处理型页面）
2. 主操作唯一性：每页仅允许 1 个主按钮，必须定义主按钮位置与触发目标；禁止同层级多个主操作抢焦点
3. 操作优先级：必须区分主操作、次操作、危险操作；危险操作不得与主操作混淆
4. 字段展示映射：必须提供“技术字段 -> 业务中文标签”映射，接口字段或数据库字段均需给出业务展示名称
5. 文案规范：文案必须面向业务用户；禁止 UI 直出技术字段名（如 `from_status`、`to_status`、`biz_id`、`user_id`）
6. 状态标签规范：状态标签必须定义颜色语义、禁用态、可点击态
7. 反馈规范：必须定义空态、加载态、失败态、成功态的反馈规则
8. 页面类型与布局模板匹配：查看型优先列表主视图、维护型优先表单主视图、处理型优先双栏处理视图
9. 主任务首屏可见：必须定义首屏可见区块，避免主任务被次任务压制
10. 滚动预算：关键任务路径滚动预算默认 <= 1 屏，超出必须注明例外理由与补偿策略
11. 列表/维护解耦：列表主任务页不得采用“上重表单下长列表”强耦合布局，优先弹窗/抽屉/Tab
12. 工具栏与分页语义：必须定义筛选 -> 结果 -> 分页顺序，并补齐分页核心元素
13. 筛选后分页重置：默认筛选后回到第 1 页，例外必须注明

4. `PRD_RAW.md` 中的 `追溯矩阵` 保留并补全，使其可直接指导接口、数据、测试设计

- 读取 `PRD_REVIEW_ISSUES.md`
- 逐条对照 `PRD_RECTIFIED.md`，验证问题是否已修复
- 输出：未关闭的阻塞问题清单

#### 4. 门禁判定
- 若任一检查失败，文档状态只能置为 `已整改`，不得置为 `已冻结`
- 输出 `PRD_RECTIFIED_GATE_REPORT.md`，说明未通过原因

#### 5. 冻结判定

- 若步骤 5.5 门禁验证结果为 `✅ 通过`，将文档状态更新为 已冻结
- 若步骤 5.5 门禁验证结果为 `❌ 未通过`，将文档状态保持为 已整改

### 步骤 6：执行需求基线冻结

在通过步骤 5 和步骤 5.5 后执行冻结确认：

1. 若步骤 5.5 门禁验证结果为 `❌ 未通过`，将文档状态置为 `已整改` 并中止下游阶段
2. 若仍有未关闭的 🔴 阻塞问题，将文档状态置为 `已整改` 并中止下游阶段
3. 若存在影响接口 / 表结构设计的 `【待确认】` 项，将文档状态置为 `已整改`
4. 若步骤 5.5 门禁验证结果为 `✅ 通过`，且阻塞问题全部关闭，且不存在阻塞设计项，将文档状态更新为 `已冻结`
5. 在变更记录中增加冻结记录（示例：`v1.0 / YYYY-MM-DD / 完成评审整改并冻结需求基线`）

### 步骤 7：提示下一步

整改完成后提示用户：

- 若 `PRD_RECTIFIED.md` 已冻结，下一步使用 `solution-design` 生成架构、接口、数据模型设计
- 若仍为 `已整改`，先回到评审问题清单继续关闭阻塞项
- 注意：`qa-design` 依赖设计文档作为输入，必须先完成 `solution-design`

## Quality Gate（分层）

### P0 Gate（阻塞，最小必检）

- [ ] 步骤 5.5 冻结前强制门禁已执行。
- [ ] 若步骤 5.5 门禁验证结果为 `❌ 未通过`，文档状态不得置为 `已冻结`。
- [ ] 所有 `🔴 阻塞` 问题已关闭；未关闭则不得冻结。
- [ ] 字段参数级约束已补齐；缺失任一项不得冻结。
- [ ] `UI约束必填块（强制）` 与后台排版约束已补齐；缺失任一项不得冻结。
- [ ] 文档状态判定正确：仅在步骤 5.5 门禁验证通过、阻塞关闭且无阻塞设计项时可置为 `已冻结`。
- [ ] 已生成 `PRD_RECTIFIED_GATE_REPORT.md`。

### P1 Coverage Checklist（扩展覆盖）

- [ ] 追溯矩阵、异常边界、非功能需求与风险标记完整。
- [ ] `【待确认】` 项已显式标注并附影响范围。
- [ ] 输出可直接供 `solution-design` 消费。

### P2 Reference Checklist（参考）

- [ ] 示例模板与说明文本已更新，且不改变 `P0` 判定口径。

## 注意事项

- 整改必须基于评审问题，不要无中生有增加需求
- 无法确定的内容标记 `【待确认】`，不要自行决定
- 字段约束必须补到参数级，不能只写“校验通过/按规范校验”
- `UI约束必填块（强制）` 缺失任一项时，文档状态不得置为 `已冻结`
- 后台排版约束缺失（布局模板/首屏可见/滚动预算/解耦策略/工具栏顺序/分页重置）任一项时，文档状态不得置为 `已冻结`
- `PRD_RAW.md` 中的“计划接口 / 计划数据表 / 计划测试”在整改阶段应尽量收敛为更明确的设计入口，但不替代正式设计文档
- 整改后的文档是后续所有设计和开发的唯一需求来源
