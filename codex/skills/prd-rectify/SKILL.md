# Skill: prd-rectify — PRD 整改

## 触发条件

当 PRD 评审完成（`PRD_REVIEW_ISSUES.md` 已生成），需要输出整改版需求文档时使用。

## 输入

1. `docs/01-requirements/PRD_REVIEW_ISSUES.md` — 评审问题清单
2. `docs/01-requirements/PRD_RAW.md` — 原始 PRD 文档

## 输出

- `docs/01-requirements/PRD_RECTIFIED.md` — 整改后的需求文档

## 执行规则

1. 冷启动规则（强制）：
   - 若目标目录不存在，先创建目录。
   - 若目标文件不存在，按本 Skill 内置结构创建完整文档。
   - 若目标文件状态为 `模板`，整文件覆盖为正式产物结构。
   - 若目标文件状态不为 `模板`，按章节标题增量更新，不按章节序号硬编码。
2. 整改必须仅针对评审问题和其直接关联项，不得扩展需求范围。
3. 对无法确认的内容必须标记 `【待确认】`，不得自行拍板。

## 执行流程

### 步骤 1：读取输入

1. 读取 `docs/01-requirements/PRD_REVIEW_ISSUES.md`，提取所有 🔴 阻塞和 🟡 重要问题
2. 读取 `docs/01-requirements/PRD_RAW.md`
3. 按章节映射整理 `PRD_RAW.md` 的关键上游结构：
   - `所属模块`
   - `状态流转`
   - `业务规则` 中的“是否影响接口/表结构”
   - `角色-权限-动作矩阵`
   - `追溯矩阵`

### 步骤 2：逐项整改

针对每个阻塞和重要问题：

1. 找到 PRD 中对应的内容
2. 按评审建议进行修改
3. 使用标记标注变更：`【新增】`、`【修改】`、`【待确认】`
4. 若问题涉及接口或数据设计前提，必须同步修正：
   - `业务规则.是否影响接口/表结构`
   - `状态流转`
   - `追溯矩阵`

### 步骤 3：补全缺失内容

检查并补全以下内容：

| 检查项 | 要求 |
|---|---|
| 功能编号 | 每个功能点必须有唯一编号（`F001`、`F002`…） |
| 角色定义 | 明确系统涉及的所有角色及权限 |
| 角色-权限-动作矩阵 | 核心角色、关键动作、数据范围和关联功能完整 |
| 业务流程 | 核心流程用文字或伪流程图描述 |
| 字段清单 | 每个表单/页面的字段必须包含类型、长度/精度、必填、默认值、最小/最大、格式/枚举、空值策略、错误提示 |
| 业务规则 | 所有业务判断逻辑必须量化和明确，并标记是否影响接口/表结构 |
| 状态流转 | 有生命周期的功能必须定义状态机；无生命周期的功能需明确“无独立状态流转” |
| 异常场景 | 每个功能点的异常流和错误提示 |
| 边界条件 | 数值范围、字符长度、数量上限等 |
| 模块展示 | 所属模块必须使用 `EN（中文）`（如 `MEM（会员管理）`） |
| 非功能需求 | 性能指标、安全要求、兼容性要求 |
| UI约束必填块（强制） | 每个功能点必须补齐页面目标与主任务、页面类型（查看型/维护型/处理型）、主操作唯一性、操作优先级、字段展示映射、文案规范、状态标签规范、反馈规范 |
| 追溯入口 | 每个功能点都能映射到计划接口、计划数据表、计划测试 |
| 验收标准 | 每条验收标准都必须可测试，不允许空泛描述 |

字段约束必填规则（每个字段按适用项补齐）：

1. 字符串：最小长度、最大长度、字符集/正则、前后空格策略
2. 数值：最小值、最大值、精度/小数位、溢出处理
3. 枚举：允许值集合、默认值、未知值处理
4. 时间：格式、时区、未来/过去时间限制
5. 空值：空值是否允许、空值默认行为
6. 错误提示：用户提示文案或错误码口径

UI约束必填规则（每个功能点必须补齐）：

1. 页面目标与主任务：必须同时定义页面目标与主任务，且必须明确页面类型（查看型页面 / 维护型页面 / 处理型页面）
2. 主操作唯一性：每页仅允许 1 个主按钮，必须定义主按钮位置与触发目标；禁止同层级多个主操作抢焦点
3. 操作优先级：必须区分主操作、次操作、危险操作；危险操作不得与主操作混淆
4. 字段展示映射：必须提供“技术字段 -> 业务中文标签”映射，接口字段或数据库字段均需给出业务展示名称
5. 文案规范：文案必须面向业务用户；禁止 UI 直出技术字段名（如 `from_status`、`to_status`、`biz_id`、`user_id`）
6. 状态标签规范：状态标签必须定义颜色语义、禁用态、可点击态
7. 反馈规范：必须定义空态、加载态、失败态、成功态的反馈规则

### 步骤 4：输出整改文档

按本 Skill 内置结构输出整改结果，并按以下映射处理上游内容：

1. `PRD_RAW.md` 中的 `所属模块`、`关联来源`、`关联澄清` 沿用到整改版
2. `PRD_RAW.md` 中的 `状态流转` 直接迁移并细化为冻结基线
3. `PRD_RAW.md` 中 `业务规则.是否影响接口/表结构` 保留，作为 `solution-design` 的设计入口
4. `PRD_RAW.md` 中的 `追溯矩阵` 保留并补全，使其可直接指导接口、数据、测试设计

### 步骤 5：交叉验证

整改完成后，对照评审问题清单逐条验证：

- [ ] 所有 🔴 阻塞问题已解决
- [ ] 所有 🟡 重要问题已解决或标记 `【待确认】`
- [ ] 功能编号完整且连续
- [ ] 模块展示字段符合 `EN（中文）`
- [ ] 每个功能点都有异常场景
- [ ] 每个有生命周期的功能都有状态流转，或明确声明“无独立状态流转”
- [ ] 业务规则中凡涉及接口 / 表结构影响的条目都已标明影响范围
- [ ] 字段清单已补齐参数级校验约束（长度/范围/精度/格式/枚举/空值策略/错误提示）
- [ ] `UI约束必填块（强制）` 已补齐，且覆盖页面目标、主任务、主操作、次操作、危险操作、字段展示映射、状态标签规则、反馈规则
- [ ] 追溯矩阵已给出接口、数据、测试的设计入口
- [ ] 每条验收标准都可测试

### 步骤 6：执行需求基线冻结

在通过步骤 5 后执行冻结确认：

1. 若仍有未关闭的 🔴 阻塞问题，将文档状态置为 `已整改` 并中止下游阶段
2. 若存在影响接口 / 表结构设计的 `【待确认】` 项，将文档状态置为 `已整改`
3. 若阻塞问题全部关闭，且不存在阻塞设计项，将文档状态更新为 `已冻结`
4. 在变更记录中增加冻结记录（示例：`v1.0 / YYYY-MM-DD / 完成评审整改并冻结需求基线`）

### 步骤 7：提示下一步

整改完成后提示用户：

- 若 `PRD_RECTIFIED.md` 已冻结，下一步使用 `solution-design` 生成架构、接口、数据模型设计
- 若仍为 `已整改`，先回到评审问题清单继续关闭阻塞项
- 注意：`qa-design` 依赖设计文档作为输入，必须先完成 `solution-design`

## 注意事项

- 整改必须基于评审问题，不要无中生有增加需求
- 无法确定的内容标记 `【待确认】`，不要自行决定
- 字段约束必须补到参数级，不能只写“校验通过/按规范校验”
- `UI约束必填块（强制）` 缺失任一项时，文档状态不得置为 `已冻结`
- `PRD_RAW.md` 中的“计划接口 / 计划数据表 / 计划测试”在整改阶段应尽量收敛为更明确的设计入口，但不替代正式设计文档
- 整改后的文档是后续所有设计和开发的唯一需求来源
